## 0. 결론 요약

1. **서버는 게임 규칙을 따로 갖고 있지 않다.** `demo/index.html`의 `<script>` 하나를 헤드리스 하네스로 그대로 실행한다. 그래서 스킬을 어떤 형태로 바꾸든 서버의 규칙은 자동으로 따라간다. 서버가 따로 들고 있는 것은 **락스텝 요약(무엇을 비교할지)**, **좌석 프레임에서 걸러 낼 항목**, **합법성 검사에서 호출할 진입점**뿐이다. [확정]
2. **스킬을 별도 js 파일(classic script)로 나눠도 서버 런타임 코드의 필수 변경은 0건이다.** 여러 파일을 싣는 일은 하네스(`demo/test/shared/harness.js`, Mars 소관)가 맡고, 서버의 `engine.js`는 그 하네스를 그대로 다시 쓴다. CSP·정적 경로 검사·MIME·Render 설정도 바꿀 필요가 없다. [확정 + 추론]
3. **서버 테스트와 요청 예산에는 필수 변경이 2건 생긴다.** ① `test-issue234-boundary.js`가 `demo/index.html` 원문에서 `V2_TIMED`·`V2_TIMED_MAG`·`resetV2`를 정규식으로 찾는다. 이 정의를 다른 파일로 옮기면 검사가 깨진다. ② `test-static-load.js`의 요청 예산 대조 목록에 스크립트 파일이 없다. 파일이 4개 이상 늘면 `security.js`의 `STATIC_BUDGET` 상수도 올려야 한다. [확정]
4. **가장 큰 위험은 로더 목록 이중화다.** 브라우저는 `index.html`의 `<script src>` 순서대로 파일을 싣는다. 하네스가 파일 목록을 따로 들고 있으면, 파일을 추가했을 때 서버만 다른 스킬 집합으로 도는 일이 조용히 생길 수 있다. 하네스의 탐욕 정규식(`<script>([\s\S]*)<\/script>`)과 태그 위치가 어긋나면 **모든 엔진 생성이 SyntaxError로 실패해 공개 대전 전체가 멈춘다**. [확정: 정규식 · 추론: 결과]
5. **서버 관점 권고:** ① 먼저 `index.html` 안에서 선언형으로 정리하는 단계를 진행한다. 서버 비용은 거의 0이고 합법성 검사와 락스텝 요약에 이득이 있다. ② 파일 분리는 그다음 단계에서 판단한다. 한다면 **3개 이하**의 classic script로 하고, **메인 스크립트보다 앞에** 두며, **하네스가 `index.html` 태그에서 목록을 읽게** 한다. ES 모듈·`fetch` JSON·스킬별 120파일·종별 30파일은 권하지 않는다(4장).

## 2. 스킬 정의를 별도 js 파일로 나눌 때 서버에 필요한 변경

전제는 `demo/skills/*.js` 같은 **classic script**다. 브라우저는 `<script src>` 순서대로 싣고, 최상위 `const`/`let`/`function`은 같은 전역 렉시컬 환경을 공유한다.

### 2.1 로더가 여러 파일을 같은 순서로 싣는 방법

| 항목 | 판단 | 근거 |
|---|---|---|
| `engine.js` 변경 | **필수 아님** | 하네스가 `fs`로 추가 파일을 읽으면 된다. `sandboxRequire`가 이미 `fs`·`path`를 허용한다(`engine.js:153`). [확정] |
| 하네스 변경(Mars 소관) | 필수 | 현재는 스크립트 블록 1개만 뽑는다. [확정] |
| 순서의 원본 | **`index.html`의 `<script src>` 태그를 문서 순서대로 파싱** | 하네스에 목록을 따로 두면 브라우저와 서버가 갈리는 구조가 생긴다(0장 4). [추론] |
| 태그 위치 | **메인 인라인 스크립트보다 앞** | 뒤에 두면 탐욕 정규식이 `</script><script src=…>`까지 삼켜 SyntaxError가 난다. 그러면 `catalog()`와 매치 시작의 `createEngine()`이 모두 예외를 던진다. [확정: 정규식 · 추론: 결과] |

| 기준판 대조 | 하네스 `opts.html`(`git show <ref>:demo/index.html`) 경로 | 분리 이전 ref에는 `src` 태그가 없으니 추가 로드도 없다. 분리 이후 ref를 메모리로 불러올 때는 스킬 파일도 같은 ref에서 읽는 옵션이 필요하다. 서버 런타임과는 무관하고 A 잡 회귀에만 해당한다. [확정: 사용처 `smoke_cross_skill.js`·`shock_compare.js` 등 · 추론: 필요] |

### 2.2 엔진 무결성·버전 일치 (해시 확인이 필요한가)

- **서버 안 두 좌석 엔진:** 같은 프로세스가 같은 디스크에서 읽으니 배포 환경에서는 같은 코드다. 다만 `load()`가 엔진마다 파일을 **다시 읽으므로**(`harness.js:156`), 로컬에서 서버를 띄운 채 `git checkout`을 하면 두 엔진이 서로 다른 파일 조합을 실을 수 있다. 파일 수가 늘수록 이 틈도 넓어진다. 그런 경우 락스텝 요약 불일치로 VOID가 되어 fail-closed로 끝난다. [확정: 매 로드 읽기 · 추론: 결과] **권고(선택):** `engine.js`에서 프로세스당 1회 소스 묶음(index + 스킬 파일)을 읽어 캐시하고, 해시를 계산해 기동 로그와 `/healthz`에 남긴다(~30~40행).
- **클라이언트↔서버(공개 방, 인증 서버):** 서버가 권위를 갖는다. 클라이언트 JS가 낡아도 **규칙 상태는 갈리지 않는다.** 대신 버튼 활성 여부와 스킬 설명 표시가 서버 판정과 달라져 `E_ILLEGAL_ACTION`이나 잘못된 설명이 나올 수 있다. 현재 프로토콜에는 규칙 빌드 버전이 없다(`protocol.js`는 `v:1` 봉투만 확인). 서버 재기동 시에는 `epoch`로 방 재개를 막는다. 이 위험은 **분리 전에도 있다.** 분리하면 "index는 새것, 스킬 파일은 옛것" 같은 **부분 불일치**가 추가로 생길 수 있다. [확정: 버전 필드 부재 · 추론: 증상]
- **기존 릴레이 락스텝(`server/server.js`, 8080, 코드 접속):** 두 **클라이언트**가 각자 엔진을 돌린다. `index.html`에서 빌드 해시·규칙 버전 비교를 찾지 못했다(`hash|digest|BUILD|rulesVer` 검색 0건). 빌드가 다른 두 클라이언트는 조용히 다른 경기를 볼 수 있고, 분리하면 그 확률이 약간 오른다. [확정: 검색 결과 · 미확인: 클라이언트 쪽 락스텝 요약 비교의 실경로 감지력]
- **판정:** 해시 확인이 **필수는 아니다.** 인증 서버는 서버 권위라 규칙 분기가 없고, 서버 응답은 `no-store`다. 다만 분리를 한다면 **규칙 소스 해시 1개**(index + 스킬 파일 이어 붙인 내용)를 만들어 두기를 권한다. 서버는 로그와 헬스 체크에, 클라이언트는 방 참가 시 비교·경고에 쓴다(클라이언트 쪽은 Mars). 비용 대비 진단 가치가 크다. [추론]

### 2.3 보안 (정적 경로 허용 목록·CSP) [확정]

- `demo/skills/fire.js` → 세그먼트 2개, `.js` 허용, 점 파일 아님, 루트 안 → **통과**. `security.js` 수정이 필요 없다.
- CSP `script-src 'self' 'unsafe-inline'` → 같은 출처 외부 스크립트는 **허용**. 수정이 필요 없다. 분리가 `'unsafe-inline'` 제거로 이어지지는 않는다. 메인 스크립트·인라인 스타일·`on*` 속성이 남기 때문이다(`security.js:475-477` 주석).
- `nosniff` + `text/javascript` → 브라우저가 스크립트 실행을 막지 않는다.
- 정보 노출: 스킬 **정의**는 지금도 `index.html` 안에서 인증 없이 제공되는 공개 자산이다. 파일을 나눠도 새로 노출되는 정보는 없다. 비공개 정보는 "어느 말이 어떤 스킬을 가졌는가"(경기 상태)이고, 이것은 `_skillsFor`가 좌석별로 거른다.

### 2.5 배포 시 캐시 불일치 위험

- **우리 서버가 직접 제공하는 경우:** 모든 응답이 `Cache-Control: no-store`다. 새로 고치면 index와 스킬 파일을 **모두 다시 받는다.** 부분 불일치 위험은 낮다. [확정: 헤더 · 추론: 브라우저 동작]
- **Render 엣지:** Web Service 응답을 CDN이 캐시하는지는 이 저장소에서 확인하지 않았다. [미확인] `no-store`를 따른다면 위와 같다.
- **배포 순간에 열려 있던 페이지:** 옛 JS가 메모리에 남는다. 인메모리 방은 재배포 때 어차피 사라진다(render.yaml 트레이드오프). 새 방을 만들면 서버는 새 규칙, 화면은 옛 설명·버튼 판정이 된다. 분리 전에도 있는 위험이다. 분리 후에는 **동시에 읽는 도중 배포가 끼면** index와 스킬 파일이 서로 다른 버전으로 조합될 수 있다. [추론] 완화: 스킬 `<script src>`에 `?v=<해시>`를 붙이거나 2.2의 해시 비교를 둔다. 쿼리 문자열은 `resolveStaticPath`가 `URL.pathname`만 쓰므로 그대로 통과한다. [확정: pathname 사용]
- **오프라인(file://):** 서버와 무관하다. classic script는 file:에서도 실린다. **ES 모듈과 `fetch`로 읽는 JSON은 file: 출처 제한으로 실패한다**는 것이 일반적인 브라우저 동작이라 CLAUDE.md의 "서버 없이 폴더째 실행" 규칙과 충돌한다. [추론: 브라우저 사양 지식 · 이 저장소 미실측] 또 하네스의 영구·외부 API 스캔 목록에 `fetch(`가 있다(`harness.js:149-151`). → **classic script만 현실적인 선택지다.**

## 4. 선언형 데이터로 바꿀 때 서버 쪽 위험과 이득

현재 사실: 스킬 **메타데이터**(이름·💪%·⌛·kind·fx 키·전투당 1회 등)는 이미 반쯤 선언형이다(`v2Reg(id,{…})`, `index.html:1038-1184`). 하지만 **효과 실행**은 `V2_FX`의 함수 객체다(`index.html:1436~`, `execV2`가 `V2_FX[sk.fx]||v2Default`로 호출, 1371-1385). 따라서 "선언형으로 바꾼다"는 말은 사실상 **효과 함수를 공통 부품 + 파라미터 데이터로 바꾸는 일**이다. [확정]

### 4.1 락스텝 요약

- **이득:** 지금은 새 지속 효과가 생길 때마다 이름을 `V2_TIMED`(엔진)와 `V2_TIMED_KEYS`(서버 사본) **두 곳에** 추가해야 한다. 경계 검사가 드리프트를 잡아 주지만 구조적인 이중 관리다. 선언형 인터프리터가 지속·세기·소유자를 **하나의 컨테이너**(예: `f.fx = {key:{r, fresh, mag, by}}`)에 담으면 요약이 그 컨테이너를 통째로 정렬 직렬화할 수 있다. 사본 목록과 해당 경계 검사를 없앨 수 있다. [추론]
- **위험 1 — 이행 기간의 감지 공백:** 새 상태가 컨테이너 밖 임시 필드로 추가되고 요약에 빠지면 **불일치가 생겨도 감지하지 못한다.** 두 엔진이 같은 코드라 분기가 곧바로 생기지는 않지만, 난수 소비가 갈리는 결함이 생기면 VOID 대신 조용히 다른 경기가 된다. 이행 기간에는 옛 필드와 새 컨테이너를 **둘 다** 요약해야 한다. [추론]
- **위험 2 — 난수 소비 순서 변경:** 공통 부품으로 합치면서 한 스킬의 `rand()` 호출 횟수나 순서가 바뀌면, 두 좌석 사이의 분기는 없어도 **같은 시드의 결과가 바뀐다.** 시드 기반 회귀와 기준판 대조(`smoke_cross_skill.js` K절 등)의 기대값이 흔들린다. 결과가 바뀐 것이 "의도된 리팩터링"인지 "결함"인지 구분하려면 이행 전후 **스킬별 결정론 대조**(같은 시드·같은 입력 → 같은 상태 요약)가 필요하다. 서버의 `lockstepDigest`를 그 대조 도구로 그대로 재사용할 수 있다. [추론]
- **위험 3 — 인터프리터 예외:** 데이터에 없는 효과 키나 잘못된 파라미터가 **경기 중에** 드러나면 `EngineFault('callback_threw')` 또는 동기 예외로 룸이 VOID(NO_CONTEST)가 된다(`engine.js:122-126`, 머리 주석 20행). fail-closed지만 경기는 사라진다. **로드 시점 스키마 검증**(모든 fx 키 존재, 필수 파라미터 타입)을 두면 서버 기동 직후 `catalog()`에서 즉시 실패해 배포 전 CI에서 잡힌다. [확정: VOID 경로 · 추론: 권고]

### 4.2 좌석 프레임 정보 경계 (미공개 스킬 비노출)

- **변하지 않는 것:** 스킬 정의는 원래 공개 자산이다. 경계는 `_skillsFor`의 좌석별 필터(자기 = 전부, 상대 = `revealedSkills`만 + 개수 없는 자리표시 1개)에 있다. 선언형으로 바꿔도 필터가 **스킬 id 문자열만** 보내는 한 경계는 그대로다. [확정]
- **위험:** ① 이행 중에 id 대신 **정의 객체나 파라미터를 프레임에 싣게 되면**(예: 클라이언트 표시 편의를 위해 `{kind, pct, cd}` 전송) 미공개 칸의 kind·등급이 다시 샌다. #234에서 막아 둔 경로다(`room.js:1048-1053` 주석). ② **스킬 칸 수 = 등급**이라는 계약(GDD-23 7.9)이 데이터 구조에 드러나는 방식이 바뀌면(예: 칸별 잠금 상태를 배열로 전송) 길이로 등급이 샌다. → 서버 화이트리스트는 **id·이름·쿨만** 유지하고, 이행 PR에서 `_skillsFor`·`_serializeBattle`의 diff를 0으로 두기를 권한다. [추론]
- **참고(현행, 새 노출 아님):** 스킬 id가 `종id-번호` 형식이라 공개된 스킬 id에서 종을 알 수 있다(`index.html:1145`). 다만 전투 무대에서 본체 출전 하수인의 `rosterId`는 이미 공개된다(`engine.js:301-307`, `room.js` side 화이트리스트). id 체계를 바꾸는 경우에만 다시 점검하면 된다. [확정: id 형식 · 추론: 영향 없음]
- **이득:** 없음(경계는 서버 필터가 결정한다).

### 4.3 합법성 검사

- **이득(가장 큼):** 지금 서버가 믿는 판정은 `slotUsable`(+`reaperWhy`)과 `V2_INTERP` 플래그다. 스킬별 사용 조건("4라운드부터", "HP 비율이 낮을 때", 전투당 1회, 봉인)이 **선언형 `req` 데이터 하나를 `slotUsable`이 평가**하는 구조가 되면, UI 버튼 활성·AI 후보·서버 합법성이 **같은 함수**를 보게 된다. UI에만 있는 조건 때문에 서버가 불법 행동을 받아들이는 부류의 결함이 구조적으로 줄어든다. [추론]
- **위험:** ① 새 조건이 `slotUsable` 밖(예: `battleModal` 버튼 렌더러)에만 구현되면 서버는 **통과시킨다.** 서버에는 그 조건을 알 방법이 없다. → "사용 조건은 반드시 `slotUsable` 경로에"를 구조 계약으로 명시해야 한다. ② 서버 `_legalAct`의 수기 분기(레거시 `'basic'`→0칸, `'skill'`→1칸, `f.skills` 없는 픽스처 폴백, 전 칸 잠김 시 pass 허용 `room.js:655`)는 칸 구조가 바뀌면 함께 고쳐야 한다. ③ 조건 평가가 `rand()`를 쓰면(현재는 없음으로 보임) 합법성 조회만으로 난수가 소비돼 좌석 엔진이 갈린다. → **조건 평가는 순수 함수**여야 한다. [확정: 현 분기 · 추론: 위험]

## 5. 서버 관점 권고와 작업 규모

### 5.1 권고 [추론 — 판단은 CJ·Venus·PD]

1. **1단계(권장): `index.html` 안에서 선언형으로 정리한다.** 파일은 나누지 않는다.
   - 서버 필수 변경: **0건**(상태 필드 이름을 유지하는 경우).
   - 함께 하면 좋은 서버 작업: 이행 전후 **스킬별 결정론 대조**(같은 시드 → 같은 `lockstepDigest`) 1회, 로드 시점 스키마 검증이 `catalog()`에서 실패하는지 확인.
   - 공통 지속 효과 컨테이너를 도입하면 요약을 컨테이너 직렬화로 바꾸고 `V2_TIMED_KEYS` 사본을 없앤다(이행 기간에는 둘 다 요약).
2. **2단계(선택): 파일 분리.** 서버는 막지 않지만 서버가 얻는 이득은 없다. 한다면 다음을 지킨다.
   - classic script **3개 이하**(예: `skills/species.js`, `skills/legend.js`, `skills/leader.js`) → 예산 상수 변경 불필요. 스킬당 120파일이나 종별 30파일은 **권하지 않는다**(공유 요청 예산 소모, 부분 캐시 조합 증가).
   - `<script src>`는 **메인 인라인 스크립트보다 앞에** 둔다. 스킬 파일은 **데이터만** 선언하고, 등록은 메인이 한다.
   - 하네스는 **`index.html` 태그에서 목록과 순서를 파싱**한다(하드코딩 금지). 원문을 이어 붙인 문자열을 `T.html`과 별도로 노출하고, 서버 경계 검사는 그 문자열을 읽는다.
   - 규칙 소스 해시 1개: 서버 기동 로그와 `/healthz`. 클라이언트 비교 여부는 Mars·PD가 판단한다.
   - ES 모듈·`fetch` JSON은 쓰지 않는다(오프라인 file: 실행 규칙과 충돌).

### 5.3 기획 방향에 따라 서버 결과가 달라지는 지점 (CJ·Venus 보고 대상 후보)

- **[기획 필요 아님 · 기술 판단]** 파일 분리 여부와 파일 수. 서버 영향은 위 표대로 작다.
- **[CJ 판단 후보]** 온라인 대전에서 **클라이언트와 서버의 규칙 빌드가 다를 때** 어떻게 할지(경고만 / 참가 차단 / 무시). 현재는 아무 처리도 없다(2.2). 스킬 수가 크게 늘어 배포가 잦아지면 체감 빈도가 오른다. 기술적 권고는 "해시 불일치 시 방 참가 차단 + 새로고침 안내"다. 다만 사용자 경험 정책이라 CJ 결정 사항이다.
- 그 밖의 특수 스킬 결함·예외(예: 사신의 낫처럼 전투를 넘는 상태, 반사/반격 한 행동 1회 게이트)는 **서버가 새로 판정하지 않고 요약·필터에만 반영**한다. 기획 방향이 바뀌어도 서버의 일은 "새 상태 필드를 요약에 넣고, 새 사용 조건이 `slotUsable`을 거치는지 확인"으로 같다. 따라서 서버 쪽에는 기획 방향별로 결과가 갈리는 별도 항목이 없다. [추론]
