## 1. 공개 룸 목록 ≠ 자동 매치메이킹 — 이 구분이 분석 전체의 축이다

CJ Comment가 예로 든 배틀넷·크레이지아케이드의 "방 목록"은 **로비 브라우징(lobby browsing)** 이다: 서버가 현재 열려 있는 방들의 메타데이터(방 이름·인원·모드·비번 유무)를 목록으로 보여주고, 플레이어가 그중 하나를 **직접 골라** 들어간다. 이는 아래 세 가지와 전부 다르다.

| 개념 | 참가 결정 주체 | 필요한 서버 기능 |
|---|---|---|
| **비공개 초대 코드** (본 설계 §2.3) | 호스트가 코드를 전달한 상대 | 룸 생성·1회용 코드·참가 |
| **공개 룸 목록 (이번 요청)** | 참가자가 목록을 보고 스스로 선택 | 위 + **룸 메타데이터 브로드캐스트·목록 조회·초대 코드 없는 참가 경로** |
| **자동 매치메이킹 (퀵매치)** | 서버가 대기열에서 짝을 고른다 | 위와 **다른 축**의 기능(대기열, 매치 기준, 취소) — 방 개념이 필요 없을 수도 있다 |

**[확정]** 현재 서버의 `waiting` 슬롯(`server/server.js:105`, `:251-263`)은 이미 자동 매치메이킹 방식이다 — 접속하면 즉시 아무나와 짝지어지고, 사용자는 방을 고르지 않는다. **[추론]** 이것과 "공개 룸 목록"은 **서로 다른 참가 흐름**이다 — 목록형은 사용자가 직접 고르고, 자동 매칭은 서버가 고른다. 목록형으로 바꾸면 이 자동 매칭 슬롯 로직은 목록 UI의 "빠른 참가(임의 룸에 자동 배정)" 버튼으로 격하되거나, 유지된 채로 룸 목록과 병존할 수 있다 — 병존은 §2 항목 4에서 확인하듯 **이미 원자적으로 설계된 좌석 점유 판정**을 두 진입 경로(코드 제시·목록 선택)가 함께 쓰는 것뿐이므로, "두 배로 복잡해진다"는 결론은 성립하지 않는다. 다만 이번 문서는 CJ가 예로 든 브라우징형에 집중하기 위해 **목록형 단일 경로**를 기준으로 서술하고, 병존 시의 UI·우선순위 정책(둘 중 무엇을 기본 화면으로 둘지)은 §218 클라이언트 영역(§7)으로 넘긴다.

**결론: CJ가 요청한 것은 매치메이킹이 아니라 목록 브라우징이다.** 이 구분이 중요한 이유는, 목록 브라우징은 본 설계의 룸 상태 기계·좌석 토큰·필드 화이트리스트를 그대로 재사용할 수 있는 반면(방을 어떻게 찾았는지는 룸 내부 로직과 무관하다), 자동 매치메이킹은 대기열이라는 **새 상태 축**을 추가로 요구하기 때문이다. 이번 분석은 전자만 다룬다.

## 2. 목록 브라우징이 초대 코드 대비 추가로 요구하는 것

본 설계 §2.3~§2.6은 "코드를 아는 사람만 들어온다"는 전제 위에서 좌석 인가·필드 은닉을 설계했다. 공개 목록은 그 전제 자체를 없애므로, **본 설계에 없던 새 표면**이 생긴다.

| # | 새 표면 | 왜 초대 코드 설계에는 없었나 | 최소 요구 |
|---|---|---|---|
| 1 | **룸 메타데이터 브로드캐스트** | 코드 모델은 룸 존재 자체를 코드 소지자 외에는 아무도 몰라도 됐다 | 서버가 `OPEN` 상태 룸의 부분집합(§4)을 모든 접속자에게 방송하거나 폴링 응답으로 제공하는 새 채널 |
| 2 | **목록 조회 채널** | 참가 경로가 코드 제시 하나뿐이었다(본 설계 §2.4.1의 `j-<코드>`) | `list_rooms` 같은 신규 명령, 또는 룸 목록을 반환하는 별도의 동적 HTTP API 엔드포인트(정적 파일 서빙과는 다른, 요청마다 현재 `OPEN` 룸을 조회해 응답하는 경로) — **좌석 토큰 발급 이전에** 응답 가능해야 목록을 보고 참가를 결정할 수 있지만, 이것이 곧 "인증 없이"를 뜻하지는 않는다. 무기명 접속 자체를 하나의 익명 세션으로 취급해 그 세션에 속도 제한을 붙이거나(§5), 필요하면 이 채널에도 가벼운 세션 인증을 둘 수 있다 — 좌석 인가(본 설계 §2.5.4)만큼 강할 필요가 없을 뿐, 반드시 무인증이어야 하는 것은 아니다 |
| 3 | **코드 없는 참가 자격** | 본 설계 §2.4.1의 `j-<초대코드>`가 유일한 참가 경로였다 | `j-` 대신 `roomId`만으로 참가하는 새 자격 형태(`p-<roomId>`류), 또는 목록 항목에 서버가 발급한 1회성 참가 토큰을 동봉 |
| 4 | **좌석 채우기 경쟁 (빈도만 다름)** | 초대 코드도 원래 여러 명이 공유하거나 동시에 제시할 수 있어 경쟁 자체는 새 문제가 아니다 — 본 설계 §2.3이 "1회용 코드 즉시 무효화·단일 동기 구간에서 판정"이라는 **원자적 좌석 점유**를 이미 공통 기반 규칙으로 요구했다(코드가 유출·공유되는 경우를 상정한 설계였다). 공개 목록이 바꾸는 것은 이 경쟁이 **드문 사건에서 상시 발생하는 정상 상황**으로 빈도가 올라간다는 점뿐이다 | 새 원자성 설계가 필요한 것이 아니라, 이미 존재하는 §2.3의 원자적 판정 로직을 "코드 제시"뿐 아니라 "목록에서 룸 선택"이라는 두 번째 진입 경로에도 동일하게 적용하면 된다 |
| 5 | **목록 갱신 전파** | 목록이 없었으므로 갱신도 없었다 | 룸이 `OPEN→SETUP`(참가로 찼음)·`OPEN→CANCELED`(호스트 이탈)·`CLOSED`(정리)로 바뀔 때마다 목록에서 빼거나 갱신하는 브로드캐스트. 본 설계 §2.3의 상태 전이 훅에 목록 갱신 부수효과를 추가하는 정도이며 새 상태 기계는 아니다 |
| 6 | **비공개 필드 노출 재검토** | 코드 모델에선 룸 존재조차 비공개였다 | 목록에 실을 필드를 §4에서 새로 화이트리스트해야 한다 — 본 설계 §2.6의 좌석 내부 필드 화이트리스트와는 **다른 표면**(룸 참가 전 익명 관측자에게 보이는 필드)이다 |

**[추론]** 이 여섯 항목은 전부 "룸이 이미 존재한다"는 본 설계의 자료구조(§2.3 상태 기계, §2.4 자격 체계) 위에 얹히는 **부가 기능**이지, 그 자료구조를 대체하지 않는다. 즉 공개 목록은 본 설계를 무효화하지 않고 확장한다 — 서버 권위 전환(본 설계 §2.2)은 공개 목록 유무와 무관하게 §1.3(숨은 정보 노출)·§1.5(행위자 강제 부재) 문제를 풀기 위해 필요하다.

## 3. 계정 선택성과 "공개 접근"은 다른 축이다

CJ Comment는 계정을 요구하지 않았지만, 협업자 주장 검토 과정에서 "누구나 들어올 수 있다"가 "누구나 아무 행동이나 할 수 있다"로 오해될 위험이 있어 명시한다.

- **[권고]** 계정 없이 공개 목록·참가를 지원할 수 있다. 참가 시 서버가 즉시 좌석 토큰(본 설계 §2.4.3)을 발급하면 되고, 그 토큰이 "이 세션이 이 좌석이다"를 증명하는 축이다. 계정은 토큰 발급 이전 단계(누가 발급받을 자격이 있는가)의 문제이며, 공개 로비는 애초에 "누구나 자격이 있다"고 답하는 모델이므로 계정 유무가 토큰 체계 자체를 바꾸지 않는다.
- **그러나 참가(좌석 점유)와 게임 내 행동 인가는 여전히 분리된 관문이다.** 좌석에 앉은 뒤에는 본 설계 §2.5.4의 행위자·소유권 검사가 **계정 여부와 무관하게** 그대로 적용된다. "공개 참가"가 "인증 없는 행동"을 뜻하지 않는다 — 좌석 토큰 자체가 그 세션의 인증이다. 이 구분이 흐려지면 "누구나 들어올 수 있으니 검사도 느슨해도 된다"는 잘못된 결론으로 미끄러질 위험이 있어 명시로 남긴다.
- **[권고] (제안)** 표시 이름(닉네임) 수집은 이번 최소안에 넣지 않고, 대신 서버가 자동 생성한 룸 레이블("방 #<roomId>" 류, §4)로 대체한다. 이는 CJ가 지시한 제약이 아니라 **Jupiter가 제시하는 초기 기본값**이며, 닉네임 입력·검열·중복 처리는 뒤에 필요해지면 추가할 수 있는 확장이지 지금 막고 있는 선결 조건이 아니다.

## 4. 최소 공개 로비 기본값 (제안, 전부 [권고])

CJ가 요구한 "최소"에 맞춰 좌석 2인·계정 없음을 전제로 목록에 실을 필드만 정한다. 아래 표의 구체값(채팅·랭킹 제외 포함)은 **전부 Jupiter의 [권고]/(제안)이지 CJ가 요구한 제약이 아니다** — CJ Comment 원문은 방 목록·자유 참가 방향만 담고 있고, 채팅·랭킹 유무는 이 문서가 범위를 좁히기 위해 제시하는 초기 기본값이다.

| 필드 | 값 | 근거 |
|---|---|---|
| 목록에 나오는 룸 | **`OPEN` 상태이며 좌석이 1개 빈 룸만** | "참가 가능한 방만 보인다"가 요청의 핵심이다. `SETUP`·`IN_PROGRESS`·`FINISHED` 룸은 목록에서 제외한다 — 진행 중인 남의 경기를 관전 목적으로 노출하는 것은 이번 범위(§2.10 "관전"과 동일하게 이 문서도 제외)가 아니다 |
| 룸 식별자 | 불투명 `roomId`(본 설계 §1.6의 `nextRoomId` 계열을 재사용하되, 참가 자격에는 이 값 단독으로 충분하도록 §2 항목 3의 새 자격 형태를 정의해야 한다) | 초대 코드를 없애는 것이 요청의 취지이므로 목록 항목 자체가 참가 키다 |
| 호스트 표시명 | **(제안, 최소 기본값)** 닉네임을 받지 않고 서버가 자동 생성한 룸 레이블("방 #<roomId>")을 대신 쓴다. 닉네임 도입은 §3처럼 나중에 추가 가능한 확장이지 지금 막힌 선결 조건이 아니다 | 목록에 뭔가는 있어야 클릭 대상을 구분하며, 자동 레이블만으로 이 목적은 충족된다 |
| 생성 시각 / 대기 시간 | 상대적 시간("3분 전") | 오래된 방 회전을 위한 최소 정보 |
| 인원 | 고정 `1/2`(2인 전제이므로 사실상 상수) | 좌석 2 고정이면 별 의미 없지만 UI 일관성상 포함 |
| 초대 코드 | (제안) 최소안에서는 목록 화면에 노출하지 않음 — **병존 자체를 배제하지는 않는다** | §2 항목 4에서 정정했듯 코드 참가와 목록 참가는 **같은 원자적 좌석 점유 판정**을 공유할 수 있으므로 병존이 "두 배로 복잡"해지지 않는다. 그럼에도 최소 범위에서는 화면 하나에 집중하는 편이 §7의 클라이언트 UI 작업량을 줄인다는 것이 이 행의 유일한 근거이며, 병존 여부는 [외부 입력](§4 마지막 행)로 남긴다 |
| 채팅 | **없음 (제안, Jupiter 초기 기본값 — CJ 지시 아님)** | 코드 모델에도 채팅이 없었으므로 최소안은 이를 신규로 추가하지 않고 유지한다. CJ가 채팅을 원하면 §7의 클라이언트 작업과 별도로 검토할 확장이다 |
| 랭킹/전적 | **없음 (제안, Jupiter 초기 기본값)** | 계정이 없는 상태에서는 전적을 특정 사람에게 귀속시키기 어려워 **최소안에서는 보류**한다 — "계정 없이는 랭킹이 존재할 수 없다"는 절대적 주장은 아니며, 세션 단위 임시 집계 등 대안이 이론상 있을 수 있으나 이 문서는 그 설계를 제안하지 않는다 |
| 비공개 룸 병존 | **[외부 입력]** — 초대 코드 방식을 완전히 대체할지, 공개/비공개 두 종류의 방을 만들지는 CJ가 정할 제품 결정이다. 이 문서는 대체를 전제로 최소안을 적었을 뿐 대체가 승인됐다고 주장하지 않는다 | §1의 병존 문제(자동 매칭 슬롯과 유사한 구조적 문제)를 되풀이하지 않기 위해 명시 |

## 5. 보안·남용 — 공개 목록이 여는 새 위협

**[추론]** 초대 코드 모델의 억제 요인 하나가 사라진다: 코드는 "이미 아는 사람만 온다"는 사실상의 접근 제한이었다(본 설계 §2.4.1의 `[추론]` 문단이 이미 "누구나 룸을 만들 수 있다"고 명시했지만, *참가*는 코드 없이는 불가능했다). 공개 목록은 **생성뿐 아니라 참가도** 완전히 개방한다.

| 위협 | 내용 | 대응 |
|---|---|---|
| 룸 스팸 생성 | 봇이 반복 생성해 목록을 도배 | 본 설계 §2.4.1의 전체 동시 룸 상한(200, 제안)·IP별 업그레이드 토큰 버킷(`server/server.js:205-208`)이 이미 커버 범위 안이다. 추가로 **IP별 동시 `OPEN` 룸 수 상한**(예: 1~2, 제안)이 필요하다 — 지금까지는 "룸을 몇 개 만드는가"가 문제되지 않았는데, 공개 목록에서는 한 IP가 목록 전체를 자기 방으로 채울 수 있기 때문이다 |
| 좌석 가로채기 경쟁 남용 | 자동화된 클라이언트가 목록을 폴링해 사람보다 먼저 모든 방에 참가 | §2 항목 4의 원자성이 "먼저 도착한 요청 하나만 성공"을 보장하긴 하지만, 그 하나가 항상 봇이 되는 것은 막지 못한다. **[권고]** 서버 쪽에서 조합 가능한 대응 옵션으로 ① 세션(익명 접속 단위)당 **동시 점유 가능 좌석 1개** 제한, ② 좌석을 점유했지만 `ready`로 넘어가지 않는 상태의 **유휴 좌석 자동 만료**(예: 30초, 제안), ③ 짧은 시간 내 반복 참가 시도에 대한 **시도 횟수 제한**(본 설계 §1.11의 `AttemptLimiter` 재사용)을 제시한다. 셋 다 익명 세션 기준이라 계정 기반 차단보다 우회가 쉽다는 한계가 있으며, 이 한계를 없애는 것(예: CAPTCHA·계정 요구)은 계정·UX 정책과 얽히는 별도 결정이라 이 문서는 강제하지 않는다 |
| 목록 조회 자체의 정찰 가치 | 목록은 "현재 몇 명이 대기 중인가"를 노출해 서비스 규모를 외부에 드러낸다 | §4 필드를 최소로 유지하는 것 자체가 대응이다. 상세 필드(호스트 IP·클라이언트 버전 등)를 목록에 절대 싣지 않는다(§2.6의 화이트리스트 원칙을 그대로 확장) |
| 참가 전 목록 조회의 부하·정찰 남용 | §2 항목 2가 지적한 채널: 좌석 토큰 발급 이전에도 목록을 볼 수 있어야 한다 | **[권고]** 목록 조회는 좌석 인가(본 설계 §2.5.4)만큼 무거운 검사를 요구하지 않는 **경량 채널**로 둔다(신규 WS 연결의 첫 프레임을 목록 요청으로 허용하거나, 별도 동적 HTTP API). 다만 이것이 "인증이 있을 수 없다"는 뜻은 아니다 — 접속 자체를 익명 세션으로 취급해 그 세션 단위로 본 설계 §1.11의 기존 요청 버킷(`server/server.js:140`)과 별도인 **목록 조회 전용 속도 제한**을 둘 수 있고, 필요하면 세션 발급 자체에 가벼운 검증을 추가할 수도 있다. 속도 제한이 없으면 목록 폴링이 무료 정찰·부하 유발 경로가 될 위험이 있다는 것이 이 행의 핵심이다 |
| 공개 참가 후 게임 내 조작 | "코드 없이 들어왔다"가 "검사를 안 받는다"로 오인 | §3에서 명시했듯 좌석 토큰 발급 이후 인가 체계(본 설계 §2.5.4)는 동일하게 적용된다. 새 위협이 아니라 §3의 재확인 |

**결론**: 공개 목록은 서버 권위 전환(본 설계 §2.2)이 이미 전제라면 **추가로 필요한 작업은 유한하다** — §2의 여섯 항목과 §5의 속도 제한 두 가지(룸 생성 IP 상한, 목록 조회 속도 제한)가 핵심이다. 이 작업들은 **본 설계 §2.3~§2.5의 기존 봉투·상태 기계·인가 프로토콜을 확장하는 것**이며 별도의 새 프로토콜 체계나 전체 재구현을 요구하지 않는다. §4·§5의 구체 기본값(레이블·유휴 만료 시간·속도 제한 수치 등)은 통상적인 서버 파라미터 선택이므로 CJ의 개별 승인 없이 구현 단계에서 조정 가능한 성격이며, [외부 입력]으로 명시한 항목(§4의 병존 여부, §3의 닉네임 확장 여부)만 CJ 결정이 필요하다. 서버 권위 전환 없이 현재의 클라이언트 시드 락스텝(본 설계 §1.2~§1.3) 위에 공개 목록만 얹으면, 상대 배치가 이미 양쪽 클라이언트 메모리에 있다는 §1.3 노출이 "아는 사람"에서 "인터넷 임의 참가자"로 넓어지므로 **권할 수 없다**. 이는 본 설계 §2.2가 이미 내린 결론과 같고, 이번 CJ의 서버 권위 승인이 바로 이 결론을 승인 범위로 넣은 것이다.

## 6. 호스팅 아키텍처 분석 — 협업자 주장 검증

CJ가 전달한 협업자 주장 세 가지를 **구조적으로만** 따진다. Mercury가 벤더별 공식 가격·쿼터를 독립 조사 중이므로 이 문서는 특정 사업자의 요금·무료 한도를 재조사하지 않는다.

### 6.1 "도메인은 선택, IP로도 동작한다"

**[확정]** 현재 클라이언트는 도메인이든 공인 IP든 **둘 다 거부**한다(본 설계 §1.9, `demo/index.html:5199-5205` — 공인 IP는 `public_ip`, 도메인은 `not_literal`로 거부). 즉 **오늘 배포된 코드 그대로는** IP로도 도메인으로도 WAN 접속이 안 된다 — 이는 §2.1이 이미 지적한 선결 변경 대상이지, IP 경로가 원천적으로 불가능하다는 뜻이 아니다.

- **[확정]** Let's Encrypt는 2026-01-15부터 **공인 IP 주소에 대한 TLS 인증서 발급을 정식 제공(General Availability)한다.** IPv4·IPv6를 지원하며 유효기간은 160시간(약 6.67일)이라 **자동 갱신이 사실상 필수**다. 출처: [Let's Encrypt 공식 발표, 2026-01-15](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability) (Mercury `hosting-evidence.md` §2가 동일 출처를 인용).
- 이에 따라 **공인 IP 직결 + 유효한 공개 CA 인증서 + `wss://`** 경로는 현재 일반적으로 실현 가능하다. **자체 서명 인증서로 우회하는 방안은 권고하지 않는다** — 브라우저가 신뢰하지 않는 인증서는 별도 수동 예외 등록을 요구해 일반 사용자 배포에 적합하지 않고, Let's Encrypt IP 인증서라는 정식 경로가 이미 있으므로 자체 서명은 불필요한 대안이다.
- **남는 것은 클라이언트·서버 화이트리스트 변경만이 아니다.** 본 설계 §1.9의 `netParseAddr()`(`demo/index.html:5199-5205`)가 공인 IP 리터럴을 거부하는 로직을 걷어내고 §2.1의 `isAllowedHost()` 화이트리스트 배선(`server/server.js:151`, `:209`)에 공인 IP 형태를 통과시키는 것은 **그중 일부일 뿐**이며, 이와 별개로 **공인 IP로의 실제 도달성 확보(방화벽 개방·포트 포워딩·라우팅), 인증서 발급·검증, 그리고 160시간 주기의 자동 갱신 운영**이 함께 필요하다. 도메인 리터럴 허용안(§2.1 원안)과 공인 IP 리터럴 허용안은 **양자택일이 아니라 병행 가능한 두 개의 개별 변경**이다.
- 짧은 유효기간(160시간)의 자동 갱신 파이프라인은 도메인 인증서의 자동 갱신(예: certbot 타이머)보다 갱신 주기가 촘촘하다는 차이가 있을 뿐, 구조적으로 새로운 문제가 아니다 — [추론].
- **결론**: 도메인 구매는 필수가 아니다. 공인 IP를 그대로 쓰는 경로는 위 변경과 운영 부담을 감수하면 일반적으로 실현 가능하고, 도메인을 쓰고 싶다면 브랜드 도메인을 새로 구매하는 대신 **호스팅 제공업체가 주는 하위 도메인**(예: `*.onrender.com`)을 그대로 쓰는 대안도 있다. 다만 두 경로의 인증서 운영 부담은 같지 않다 — **제공업체 하위 도메인 경로만 관리형 TLS 제공이 확인됐고(Render, Mercury `hosting-evidence.md` §2·§3)**, **자체 공인 IP 경로는 160시간 주기 인증서 발급·갱신을 직접 운영하거나 이를 대신해줄 서비스와 별도로 계약해야 한다.** "정적 프런트엔드만 도메인이 선택이고 WSS 백엔드는 도메인이 필요하다"는 구분은 근거가 없다 — 백엔드도 IP 인증서 경로로 도메인 없이 서비스할 수 있으나, 그 경로의 인증서 운영은 제공업체 하위 도메인 경로보다 부담이 크다.

### 6.2 "ngrok 같은 무료 터널로 테스트 가능"

**[확정]** ngrok 및 유사 리버스 터널은 **로컬(또는 임의 사설망)에서 실행 중인 프로세스**를 외부에서 접근 가능한 주소로 노출하는 도구다 — 터널이 유지되려면 터널을 여는 origin(서버 프로세스와 ngrok 에이전트)이 계속 실행 중이어야 한다. 이는 어떤 티어를 쓰든 이 도구 범주 자체의 구조이며, 이 문서는 이전 판에서 이를 "임시·무작위 주소만 가능"·"상시 운영 불가"로 과장해 서술했던 것을 정정한다.

- **[확정]** ngrok 공식 문서 기준으로 무료 플랜은 **할당된 안정적 개발 도메인(assigned stable dev domain) 1개**를 제공하며, 이는 매 재시작마다 무작위로 바뀌는 방식이 아니다. 무료 endpoint 자체에 **강제 시간 만료(endpoint timeout)는 없다**. 출처: [ngrok 무료 플랜 한도](https://ngrok.com/docs/pricing-limits/free-plan-limits) (Mercury `hosting-evidence.md` §1과 동일 출처).
- **[확정]** ngrok은 같은 HTTP endpoint에서 **WebSocket을 지원**하며 외부에서는 `wss://`로 접속한다. 출처: [ngrok과 WebSocket](https://ngrok.com/docs/using-ngrok-with/websockets) (Mercury `hosting-evidence.md` §1).
- 무료 플랜에는 월 outbound 1GB·HTTP 요청 20,000회 등 **할당량**이 있고, 터널이 실제로 살아 있으려면 **origin 컴퓨터가 계속 켜져 있어야 한다**(PC 절전·종료·재부팅·네트워크 단절 시 함께 끊긴다). 이는 사업자 정책이 아니라 리버스 터널이라는 구조 자체의 성질이다.
- **[권고]** 따라서 ngrok을 상시 운영에 권하지 않는 것은 "이 도구가 임시 주소만 지원해서"가 아니라, **① origin 컴퓨터를 24/7 켜 둬야 하는 운영 부담, ② 무료 할당량이 상시 트래픽을 감당하도록 설계되지 않았다는 점**이라는 **운영상의 이유**다. 개발 중 짧은 검증에는 안정적 도메인·무료 HTTPS/WSS·시간 제한 없음이 오히려 적합한 근거가 되고, 이 문서는 "개발·테스트 단계 후보로 타당하다"는 결론을 유지하되 "상시 운영이 원천적으로 불가능하다"는 주장은 하지 않는다.

### 6.3 "HTML 게임 포털이 도메인을 제공하므로 비용이 안 든다"

이 주장은 **정적 프런트엔드**와 **상시 실행 WebSocket 백엔드**를 구분하지 않는다. 이 게임은 후자를 필수로 요구한다(본 설계 §1.1 — 서버가 릴레이하고, 서버 권위 전환 후에는 규칙 판정까지 서버가 한다).

| 배포 대상 | 포털이 실제로 제공하는 것 | 이 게임에 충분한가 |
|---|---|---|
| **정적 자산**(HTML/CSS/JS, `demo/index.html` 자체) | 다수의 HTML 게임 포털·정적 호스팅 서비스가 이 부분은 도메인·CDN·HTTPS를 함께 제공한다 — **[추론]**, 일반적인 정적 호스팅 서비스 모델이며 특정 사업자를 지목해 검증하지 않았다 | **부분적으로 충분** — 정적 페이지 서빙 자체는 포털 인프라로 해결될 수 있다 |
| **iframe 임베드** | 포털이 자기 도메인 아래 `<iframe>`으로 게임을 감싸는 방식이 흔하다 — **[추론]** | **WebSocket 연결 자체와는 무관하다.** iframe은 페이지를 감쌀 뿐, 그 안의 JS가 여는 `wss://` 연결은 여전히 **게임 자신의 백엔드**를 향해야 한다. 포털이 게임 로직 서버를 대신 운영해주지 않는 한(그런 계약이 있다는 근거는 없다), 이 부분은 그대로 남는다 |
| **상시 실행 WebSocket 백엔드**(룸 상태·규칙 판정을 갖는 서버, 본 설계 §2.2) | **[추론]** 정적 호스팅·포털이 이 역할을 대신 제공한다는 근거를 찾지 못했다. 일반적으로 정적 호스팅과 상태를 갖는 백엔드 프로세스 호스팅은 **별개의 서비스 카테고리**다 | **불충분** — 이 부분은 포털·정적 호스팅과 무관하게 별도로 상시 실행 환경이 필요하다 |

**결론**: "포털이 도메인을 제공하니 비용이 안 든다"는 주장은 **정적 프런트엔드 배포 비용**에는 타당성이 있을 수 있지만(그마저 특정 포털 계약 조건에 따라 다르며 이 문서는 검증하지 않았다), **이 게임이 필요로 하는 상시 실행 WebSocket 백엔드**(룸 상태·규칙 판정, 서버 권위 전환의 본질)는 정적 호스팅·포털 임베드로 대체되지 않는다. 이는 특정 사업자 가격표를 몰라도 성립하는 아키텍처 구분이며, 실제 비용·사업자 선정은 본 설계 §4의 [외부 입력](배포 호스트·도메인, 월 비용 상한, TLS 종단 책임)과 Mercury의 벤더 조사 영역이다 — 이 문서는 그 숫자를 추정하지 않는다.

## 7. #218(클라이언트 로비 UI) 의존성

- **[확정]** 이 문서 작성 시점에 `docs/milestone/v0.4.10/issues/217/`에는 #218 관련 산출물이 없다 — Venus의 Notion 동기화 기록(`docs/milestone/v0.4.10/issues/217/Venus/notion-sync.md:32`, `:345`)이 "#218 로비"를 v0.4.10 계획 항목으로만 언급할 뿐, 기획·구현 착수 문서는 확인되지 않았다.
- **[추론]** §4의 최소 로비 필드(목록 항목·참가 버튼)는 **클라이언트 UI가 그릴 화면 자체**이므로, 서버가 §2·§4·§5의 프로토콜(목록 조회 채널·참가 자격 형태)을 확정하기 전에 클라이언트가 화면을 구현하면 재작업 위험이 있다. 반대로 서버가 이 문서 없이 임의로 프로토콜을 확정하면 클라이언트 요구(예: 목록 갱신 주기, 페이지네이션 필요 여부)를 놓칠 수 있다.
- **[권고]** #218이 정식으로 분석되기 전까지 §4·§5는 서버 관점의 **초안**으로만 취급한다. Mars(클라이언트 구현)와의 필드·이벤트 이름 합의가 선행돼야 §2 항목 1·2(브로드캐스트 채널, 목록 조회 명령)의 정확한 스키마를 확정할 수 있다.
- 이 문서는 클라이언트 작업을 대신 설계하지 않는다(역할 계약 — Jupiter=SERVER, 클라이언트는 Mars 영역).

## 8. 이 문서가 확정하지 않는 것

이 문서의 결론(§0 도입부 — "실현 가능하며 권고")은 **아키텍처·프로토콜 관점의 실현 가능성**이다. 아래는 그와 별개로 확정하지 않은 것들이다.

- **공개 로비가 비공개 코드 방식을 완전히 대체할지, 병존할지**는 외부 입력(§4) — §1·§2 항목 4에서 정정했듯 병존이 기술적으로 두 배 복잡한 것은 아니므로, 이 결정은 순수 제품 판단이다.
- **작업량·일정을 추정하지 않았다.** 본 설계 §5와 동일한 원칙.
- **특정 호스팅 사업자·가격·무료 한도를 조사하지 않았다.** Mercury의 독립 조사 영역이며 중복하지 않는다.
- **CJ 승인·Saturn QA 통과를 주장하지 않는다.** 이번 CJ Comment가 승인한 것은 "서버 권위 전환 방향"뿐이며, 공개 로비의 필드·상태 기계·보안 대책은 전부 [권고]로 남아 있다.
- **자동 매치메이킹(퀵매치) 설계는 다루지 않는다.** §1에서 구분했듯 다른 기능이며, 본 설계 §2.10이 이미 별도 안건으로 미뤄뒀다.
