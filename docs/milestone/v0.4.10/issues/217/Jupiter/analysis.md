# #217 — HTML 외부망 비공개 룸 서버 구조: Jupiter_Server 설계안

- 작성: Jupiter_Server (Claude Opus 5, high), 2026-09-13. 이전 두 판(Sonnet 5 medium)에서 같은 원인의 정합성 결함이 반복돼 **누적 패치가 아니라 전면 재작성**으로 교체한 판이다. 이전 판의 확인된 사실·출처는 보존하고, 서로 어긋나던 정책 서술과 이미 기본값이 정해진 "열린 질문"은 제거했다.
- 범위: `mutation=docs`. 코드·Git·GitHub·Notion 쓰기 없음. 이 파일 한 개만 갱신한다.
- 이슈 본문의 "Jupiter 분석 결과"는 Mercury_PD가 직접 작성한 기술 벤치마크이며 [HANDOVER_SNAPSHOT.md](../../../../../creat2ve/HANDOVER_SNAPSHOT.md)에서 **비권위**로 명시됐다. 이 문서는 그 결과를 승계하지 않고 `server/`·`demo/index.html` 원본을 직접 읽어 다시 세웠다.
- 2026-09-13 델타 개정: Saturn 1차 검수가 지적한 여섯 개의 유한한 정합성 결함만 고쳤다 — ① 등급 C "전체 레코드"의 미공개 기술·내부 필드 노출(§2.6·§2.6.1·§2.6.2) ② `setupPlayer` 게이트와 좌석 독립 배치의 충돌(§2.5.4) ③ 에폭을 나르지 않는 재개 자격(§2.4.1.1) ④ 회전 응답 반복 유실 시 영구 잠김(§2.4.3) ⑤ 명시적 `leave`와 소켓 단절의 미분리·이중 승리(§2.3.1) ⑥ 상태 개수 주장과 부분 문자열 검증(§2.3·§3). 전면 재작성이 아니며 새 기능을 넣지 않았다. 대응 수용 기준 행은 §3에 A6·A7·B6·D5·F6·F7·G3으로 추가했다.
- 검토 상태: **CJ 미승인 · Saturn 독립 QA 미실시.** 이 문서는 제안이며, 승인·검증을 받은 바 없다. 이번 개정으로 바뀐 정책도 전부 [권고]이고 승인 대상이다.

## 1. 현재 상태 — 검증된 사실 [확정]

소스: `server/server.js`, `server/security.js`, `demo/index.html` (`milestone/v0.6.0` HEAD `8bb6d98` 기준).

### 1.1 서버는 내용을 해석하지 않는 1:1 릴레이다
메시지 핸들러는 `S.validateRelayMessage()`로 크기·형식만 검사하고 통과한 바이트를 그대로 상대에게 넘긴다(`server/server.js:275-284`, 주석 "서버는 내용을 해석하지 않는다"). 게임 규칙 판정은 서버에 없다.

### 1.2 동기화는 클라이언트 시드 락스텝이다
P1이 시드를 만들어 `hello`로 보내고 P2가 `hello2`로 응답한 뒤, 양쪽이 `setSeed(seed)`로 같은 RNG를 공유하고 각자 로컬에서 같은 로직을 재계산한다(`demo/index.html:5316-5334`, `setSeed`/`rand` 정의는 `demo/index.html:729-733`).

### 1.3 숨은 정보는 이미 양쪽 클라이언트 메모리에 다 있다
`netStart()`는 `applyNetSetup(0, setups[0])`과 `applyNetSetup(1, setups[1])`을 **양쪽 클라이언트 모두**에서 실행한다(`demo/index.html:5328-5329`). 두 클라이언트가 상대의 전체 배치를 처음부터 들고 있고, 화면 표시만 가린다. 개발자 도구로 `S.pieces`를 읽으면 상대 배치가 즉시 드러난다.

### 1.4 가시성은 "위치"와 "정체" 두 개의 독립된 관문이다 — 이 구분이 이 설계의 핵심 근거다
이전 판이 "위치는 보이되 정체는 미공개"라는 중간 상태를 *있는지 확인이 필요한 가정*으로 적었으나, 그 상태는 **현재 게임의 기본 동작이다**.

```js
function visibleTo(viewer,e){          // demo/index.html:1361-1366
  if(e.owner===viewer) return true;
  if(!inForest(e)) return true;        // ← 숲 밖의 말은 상대에게도 "위치"가 항상 보인다
  if(S.tempReveal.has(e.id)) return true;
  return alivePieces().some(m=>m.owner===viewer&&adj(m,e));
}
```

렌더 경로(`demo/index.html:1707-1712`)는 이 둘을 명시적으로 분리한다:

```js
if(p&&(ghost||viewer===2||visibleTo(viewer,p))){          // 1707 — 그릴 것인가(=위치 노출)
  const known = viewer===2||p.owner===viewer||p.revealed;  // 1709 — 정체를 알 것인가
  ...
  chip.innerHTML = known ? pcBodyHtml(p) : (추측 이모지 또는 "?");  // 1717-1719
```

따라서 실제 가시성 등급은 **세 단계**다.

| 등급 | 판정 | 상대가 아는 것 |
|---|---|---|
| A. 안 보임 | `visibleTo` 거짓 — 숲 안 + 인접 없음 + `tempReveal` 없음 | 아무것도. 그 칸에 말이 있다는 사실조차 몰라야 한다. |
| B. 보이지만 미식별 | `visibleTo` 참 + `known` 거짓 | 좌표·소유자·생존. 정체(`type`/`name`/`element`)와 **HP는 모른다**. |
| C. 공개 | `p.owner===viewer` 또는 `p.revealed` | 전부. |

- HP가 B에서 새지 않는다는 것도 코드 사실이다: HP 문자열은 `pcInfoHtml()`이 만들고(`demo/index.html:1209-1214`) 이는 `pcBodyHtml()`을 통해 **`known` 분기에서만** 호출된다(`demo/index.html:1716-1717`). 접근성 라벨도 `known`일 때만 붙인다(`demo/index.html:1720`).
- `revealed`는 초기 false이고(`demo/index.html:1303`) 함정 발동(`:2784`)·전투 개시(`:2840`, `:2924`)·포획(`:2507`) 등 **규칙상 공개 사건**에서만 true가 된다.
- `viewer===2`는 시뮬레이션/관전 시점이며 온라인 대전 경로에는 해당하지 않는다(`demo/index.html:1345` `humanViewer()`는 온라인에서 항상 `NET.me`를 돌려준다).

### 1.5 입력 주체는 "현재 턴 플레이어"가 아니다 — 이미 별도 함수가 있다
```js
function netActor(){                                    // demo/index.html:4951-4958
  if(S.phase==="setup") return S.setupPlayer;
  if(S.battle) return (actorOfPhase()==="A"?S.battle.attP:S.battle.defP).owner;
  if(S.fleePick) return S.fleePick.owner;               // 방어자일 수 있다
  return S.current;
}
```
- `S.fleePick.owner`가 `S.current`와 다를 수 있음은 상태 정의 주석이 명시한다(`demo/index.html:1271`).
- 전투 중 행동 순서는 `actorOfPhase()`가 라운드·감전 상태로 결정한다(`demo/index.html:2942-2948`).
- **`resign`만은 예외로 `S.current` 기준이다**: `(a.t==="resign"?S.current:netActor())!==NET.me` (`demo/index.html:4967`).
- 이 구분은 현재 **클라이언트 UI 게이팅으로만** 강제된다(`demo/index.html:4967`의 송신 거부, `:1791-1793`·`:1814-1816`의 버튼 비활성). 서버는 검사하지 않으므로 개발자 도구로 우회할 수 있다.

### 1.6 서버는 이미 다중 동시 매치를 지원한다 — 없는 것은 "룸 객체"다
`waiting`(`server/server.js:105`)은 큐가 아니라 "다음 상대를 기다리는 한 명" 슬롯이며, 매칭 즉시 비워지고(`:251-263`) 다음 접속자가 다시 채운다. 한 프로세스가 여러 쌍을 동시에 릴레이한다. 실질 상한은 룸 로직이 아니라 `LIMITS.maxConnections`(기본 16)·`maxConnectionsPerIp`(기본 4)다(`server/server.js:75-90`). 다만 `nextRoomId`(`:106`, `:252`)는 클라이언트에 통지하는 불투명 정수일 뿐이고, **서버가 ID로 조회·추적하는 룸 자료구조는 없다**.

### 1.7 재접속 경로가 없다
소켓이 닫히면 `ws.on('close')`가 상대에게 `opponent_left`를 보내고(`server/server.js:287-297`), 클라이언트는 이를 즉시 몰수패로 처리한다(`demo/index.html:5310-5315`). 유예·토큰·재입장이 전혀 없다.

### 1.8 인증은 WebSocket 업그레이드 단 한 곳뿐이고, 그 통로의 형태가 고정돼 있다
- 접근 코드는 `Sec-WebSocket-Protocol` 하위 프로토콜 토큰으로만 전달된다(`server/server.js:219-229`). 쿼리·쿠키·URL 경로는 읽지 않는다.
- `presentedAccessCode()`는 **정확히 2개 토큰**일 때만 성립하고 첫 토큰이 공개 마커 `digit-duel.v1`여야 한다(`server/security.js:148-155`, 마커는 `:116`).
- 토큰 문자 집합은 RFC 7230 token(`server/security.js:121`), 토큰당 최대 64자·최대 4개(`:118-119`).
- 서버는 응답에 **공개 마커만** 되돌린다(`server/security.js:158-161`, 이유 주석 `server/server.js:188-192`) — 비밀값이 `ws.protocol`·프록시 로그로 반향되지 않게 한 설계다.
- 코드는 매 기동마다 새로 생성되고 저장소에 없다(`server/server.js:44-61`).
- **[추론]** 이 통로는 "이미 알고 있는 값을 제시"하는 형태만 지원한다. 서버가 *새 자격을 발급*하는 경로는 업그레이드 단계에 없다 — §2.4.1의 부트스트랩이 이 공백을 메운다.

### 1.9 클라이언트 주소 정책이 공인 도메인을 거부한다
`netParseAddr()`는 `localhost`·사설 IPv4/IPv6만 허용하고 공인 IP는 `public_ip`, 도메인 이름은 `not_literal`로 거부한다(`demo/index.html:5199-5205`). 서버 쪽 `isAllowedHost()`는 `extraHosts` 화이트리스트를 이미 지원하지만(`server/security.js:286-299`) 호출부 두 곳이 인자를 넘기지 않아 죽어 있다(`server/server.js:151`, `:209`). `isSameOrigin()`은 Origin의 host와 `Host` 헤더가 문자열로 일치해야 통과한다(`server/security.js:272-283`). 바인드는 공인 IP를 거부한다(`server/server.js:29-42`).

### 1.10 접속 코드는 탭 메모리에만 산다
`NET.code`는 입력칸에서 메모리로 옮긴 뒤 DOM을 비우고(`demo/index.html:5211-5219`), 어떤 저장소에도 쓰지 않으며 매치 종료·협상 실패 시 버린다(`demo/index.html:1995`, `:5270`, `:5294`). 주소만 `localStorage`에 남긴다(`demo/index.html:5243`).

### 1.11 하드닝은 이미 상당하다
IP별 HTTP/업그레이드 토큰 버킷, 연결 수 상한, 메시지 크기 상한, 인증 실패 누적 차단(`AttemptLimiter`), 실패 사유 비노출(`server/server.js:194-200`)이 구현돼 있다. **[추론]** 이 설계는 LAN 전제이며 WAN 위협 모델에 대해 재검증된 적은 없다.

### 1.12 정적 서빙은 무인증, 테스트 스위트는 존재한다
정적 클라이언트는 코드 없이 누구나 받는다(`server/server.js:127-171`). 보호 대상은 WS 릴레이뿐이다. `npm test`는 `test.js`·`test-security.js`·`test-config.js`·`test-launcher.js`·`test-static-load.js`를 돌린다(`server/package.json:8`). 헬스체크 엔드포인트는 없다(`server/server.js` 전체에 `/healthz` 없음).

## 2. 권고 설계 — 초대 코드 비공개 룸 [권고]

이 장 전체가 **하나의 정합적인 번들**이다. 대안 분기를 제시하지 않는다 — §2.2의 방향을 기각하면 §2.6의 보안 효과가 성립하지 않으므로, 부분 채택은 설계가 아니라 절충이며 그 판단은 CJ가 별도로 내려야 한다.

### 2.1 WAN 개방의 선결 변경 (§1.9의 결과)

"리버스 프록시로 TLS만 얹으면 된다"는 전제는 현재 코드에서 성립하지 않는다. 아래는 최소 변경 목록이다.

| 위치 | 현재 | 필요 변경 [권고] |
|---|---|---|
| `netParseAddr()` `demo/index.html:5169-5205` | 도메인·공인 IP 거부 | 배포 빌드에서만 켜지는 **도메인 리터럴 허용** 분기. 공인 IP 리터럴은 계속 거부 — TLS 인증서 호스트명 검증·`isSameOrigin`의 Host 비교와 맞물리고, DNS를 두면 이후 IP 교체를 흡수한다. |
| `isAllowedHost()` 호출부 `server/server.js:151`, `:209` | `extraHosts` 미전달로 기능이 죽어 있음 | 배포 도메인을 `DD_PUBLIC_HOST`(제안 이름)로 받아 두 호출부 모두 `S.isAllowedHost(req.headers.host, [DD_PUBLIC_HOST])`로 전달. 기존 사설/루프백 허용은 유지. |
| `resolveBindAddress()` `server/server.js:29-42` | 공인 IP 바인드 거부 | **변경하지 않는다.** 리버스 프록시가 443을 받고 백엔드는 루프백으로 두면 이 제한이 그대로 유효한 방어로 남는다. |
| `isSameOrigin()` `server/security.js:272-283` | Origin host = Host 문자열 일치 요구 | 코드 변경 없음. **배포 요구사항**: 프록시가 원본 `Host`를 리라이트하지 않고 그대로 전달해야 한다(nginx `proxy_set_header Host $host;` 상당). 누락되면 정상 브라우저 요청도 403이 된다. |
| `netServerDefault()` `demo/index.html:5207-5209` | `location.host` 기본값 | 변경 불필요. 배포 도메인에서 서빙되면 올바른 기본값이 나오므로 사용자가 주소를 손으로 넣을 일이 없어진다. |
| 헬스체크 | 없음(§1.12) | `GET /healthz` 신설(제안). 인증 없이 200/503만 반환하고 내부 상태는 싣지 않는다. |

### 2.2 아키텍처: 서버 권위로 전환한다

두 문제를 구분한다.

- **기밀성** — 중간자가 통신을 읽는가. TLS(`wss://`)로 해결되며 서버 권위와 무관하다. 클라이언트는 `https:` 페이지에서 이미 `wss://`를 시도한다(`demo/index.html:5245`).
- **노출** — 클라이언트가 몰라야 할 정보를 *실제로 갖고 있는가*. §1.3의 문제이며 TLS로는 해결되지 않는다.

**[추론]** 기술적으로는 현행 릴레이 구조에 TLS만 얹어 WAN을 열 수도 있다. 그러나 그 경우 §1.3의 노출 범위가 "같은 공유기의 지인"에서 "인터넷상 누구나"로 넓어지고, 그 상태로 "숨은 정보를 보존한다"고 말하면 사실과 어긋난다. 또한 §1.5의 행위자 소유권 강제가 클라이언트 UI에만 있으므로, 상대 소유 유닛의 선택을 대신 보내는 조작도 막히지 않는다.

**[권고]** 서버가 룸 상태를 소유하고, 각 좌석에 §2.6의 화이트리스트를 통과한 뷰만 보낸다. 구현 경로는 `demo/index.html`의 순수 규칙 로직(이동·전투·상성·폭탄·함정·밀어내기·판정·`visibleTo`)을 **서버와 클라이언트가 공유하는 단일 JS 모듈**로 분리하는 것이다 — Node 서버이므로 언어 재작성이 필요 없고, 규칙이 두 벌로 갈라지는 위험을 피한다. `CLAUDE.md`가 요구하는 헤드리스 스모크 테스트를 그 모듈 기준으로 옮겨야 회귀를 잡는다.

**[확정]** 이는 작은 변경이 아니다. `demo/index.html`의 규칙 로직은 전역 `S`와 DOM 렌더가 같은 함수 안에 섞여 있는 지점이 많다(예: `onCell` 계열이 `render()`를 직접 호출). 분리 자체가 별도 구현 이슈 규모다.

### 2.3 룸 생명주기

**READY는 상태가 아니다.** 상태 라벨은 아래 일곱이다 — `OPEN`·`SETUP`·`IN_PROGRESS`·`FINISHED`·`CANCELED`·`VOID`·`CLOSED`. READY는 그중에 없다: 좌석별 불리언 두 개일 뿐이고, 이를 상태로 승격시킨 것이 이전 판에서 "재접속 시 ready 유지/양측 리셋/한쪽 리셋"이 동시에 적혀 충돌한 원인이다. 경기 **결과**(`WIN`·`FORFEIT`·`NO_CONTEST`)도 상태가 아니라 `FINISHED`가 싣는 값이다(§2.3.1).

```
OPEN ──(게스트 참가)──> SETUP ──(양측 ready)──> IN_PROGRESS ──(승패/기권)──> FINISHED ──(정리)──> CLOSED
  └─────────────────────── CANCELED (결과 없음) ───────────────┘
  └─────────────────────── VOID (서버 재시작, §2.8) ───────────┘
```

| 상태 | 들어오는 조건 | 이 상태에서 허용되는 명령 | **소켓 단절** 유예 만료 결과 (명시적 `leave`는 §2.3.1) |
|---|---|---|---|
| `OPEN` | 룸 생성. 호스트 1인. 초대 코드 유효. | `reissue`(초대 코드 재발급), `leave` | **CANCELED** (지킬 경기가 없다) |
| `SETUP` | 게스트가 초대 코드로 참가. 좌석 2개 확정. | `setup`(자기 배치 갱신), `ready`/`unready`, `leave` | **CANCELED** (아직 시작 전이므로 승패 없음) |
| `IN_PROGRESS` | 두 좌석 `ready===true`를 한 번의 동기 검사로 확인 | `action`(§2.5), `resign`, `resync` — **`leave` 없음**(§2.3.1) | **상대 좌석 몰수승**(`FINISHED` + `FORFEIT`). 두 좌석이 모두 끊긴 경우는 §2.3.1 |
| `FINISHED` | 승패 확정 | `resync`, `leave` — `leave`는 결과를 바꾸지 않고 그 좌석의 소켓만 닫는다(§2.3.1) | 없음 (결과는 이미 확정) |
| `CLOSED` | FINISHED 후 5분(제안), 또는 CANCELED/VOID 즉시 | 없음. 룸 삭제, 모든 좌석 토큰 폐기 | — |

**게스트 이탈의 단일 규칙**: 게스트가 `SETUP`에서 이탈해 유예가 만료되면 룸은 `CANCELED`가 된다. "호스트만 남아 `OPEN`으로 되돌아간다"는 별도 경로를 두지 않는다 — 되돌아간 룸의 좌석 번호·배치·ready를 어떻게 승계할지가 또 하나의 규칙 집합을 만들고, 이전 판의 모호함이 정확히 거기서 나왔다. 호스트는 `CANCELED` 후 새 룸을 만들면 되고, 그 비용은 초대 코드 한 번 더 전달하는 것뿐이다.

**초대 코드**
- 형식: 6자 대문자 영숫자, `0 O 1 I L` 제외(제안). 이 문자 집합은 RFC 7230 token 안전 집합의 부분집합이므로 §1.8의 하위 프로토콜 통로로 그대로 나른다.
- 유효 기간: `OPEN` 상태에서 10분(제안). 만료되면 룸은 `CANCELED`.
- **1회용**: 첫 참가 성공 즉시 무효화한다. 코드가 유출돼도 이미 찬 방에 제3자가 들어올 수 없다.
- `reissue`: 호스트가 요청하면 구 코드를 **즉시** 무효화하고 새 코드를 발급한다(구 코드 제시 → `E_ROOM_NOT_FOUND`). TTL은 새로 시작한다.
- 서버 전체 접근 코드(`ACCESS_CODE`, §1.8)와 이름공간을 공유하지 않는다.

**READY의 단일 규칙**
- 좌석별 불리언. **그 좌석이 자기 배치를 바꿀 때만** 자기 ready가 false로 돌아간다.
- **재접속은 ready를 건드리지 않는다.** 상대 좌석의 ready는 어떤 경우에도 서버가 임의로 내리지 않는다.
- 시작 판정의 경쟁 상태는 리셋이 아니라 원자성으로 막는다: 서버는 `ready` 명령을 처리하는 **하나의 동기 함수 안에서** 두 불리언 확인 → 배치 스냅샷 고정 → `IN_PROGRESS` 전이까지 끝낸다. Node.js의 JS 실행은 단일 스레드이므로 `await` 경계가 없는 동기 구간에는 다른 요청 처리가 끼어들지 않는다. 전이 이후의 `setup`/`ready`/`unready`는 `E_MATCH_STARTED`로 거부한다.
- 상대의 ready **불리언 자체는 공개한다**. "상대 준비 완료, 시작 대기 중" 표시가 없으면 UI가 성립하지 않고, 현행 `hello`/`hello2` 교환에서도 상대가 제출했다는 사실은 이미 서로 안다(`demo/index.html:5316-5319`). 감춰야 하는 것은 **배치 내용과 배치한 개수**이지 제출 여부가 아니다(§2.6).

**이탈 유예**
- 좌석 소켓이 닫히면 그 좌석의 유예 타이머가 시작된다(60초, 제안). 상태와 무관하게 같은 타이머를 쓴다.
- 유예 안에 같은 좌석 정체로 재접속하면 타이머를 취소하고 그대로 잇는다.
- 상대 화면에는 "상대 연결 재시도 중 (남은 시간)"만 표시하고 이탈 사유는 보내지 않는다.

#### 2.3.1 이탈의 두 경로 — 명시적 `leave` vs 소켓 단절 [권고]

두 사건을 같은 타이머로 묶으면 "나갔다"와 "끊겼다"가 구별되지 않는다. 분리한다.

| 사건 | 뜻 | 처리 |
|---|---|---|
| 명시적 `leave` 프레임 | 좌석의 **의사 표시**. 클라이언트가 보낸 명령이다. | 유예 타이머를 쓰지 않는다. `OPEN`·`SETUP`에서 **즉시 `CANCELED`**로 가고 룸을 그 자리에서 정리한다. |
| 소켓 단절 (close·타임아웃) | 의사 표시가 아니다. 일시적 네트워크 사건일 수 있다. | 그 좌석의 유예 타이머(60초, 제안)가 시작된다. 유예 안에 재개하면 그대로 잇고, 만료하면 위 상태표의 결과가 난다. |

- `IN_PROGRESS`에는 `leave`가 **없다**. 경기를 떠나는 유일한 명시 경로는 `resign`이고 결과는 상대 승리(`FINISHED` + `WIN`)다. `IN_PROGRESS`에서 `leave` 프레임이 오면 `E_ILLEGAL_ACTION`으로 거부한다 — 소켓을 끊고 유예를 기다리는 것보다 유리한 즉시 탈출구를 만들지 않기 위함이다.
- `FINISHED`에서의 `leave`는 결과를 바꾸지 않는다. 그 좌석의 소켓을 닫을 뿐이다.

**두 좌석이 모두 끊긴 경우 — 판정은 한 번뿐이다.**
- `IN_PROGRESS`에서 두 좌석의 유예가 동시에 돌 수 있다. 이때 **먼저 만료된 좌석에 대해서만 한 번 판정**하고 룸을 그 자리에서 `FINISHED`로 옮긴다. 결과는 `FORFEIT`, 승자는 나머지 좌석이다.
- 나중에 두 번째 좌석의 타이머가 만료되면 룸이 이미 `FINISHED`이므로 **아무 일도 하지 않는다.** 좌석마다 독립으로 몰수 판정을 돌려 양쪽에 승리를 주는 경로는 존재하지 않는다 — 임의의 이중 승리는 이 순서 규칙 하나로 닫힌다.
- 두 만료가 **같은 틱**이라 선후를 정할 수 없으면 결과는 `NO_CONTEST`다. `FINISHED`로 가되 승자를 기록하지 않는다. 동전을 던져 한쪽을 고르지 않는다.
- `WIN`·`FORFEIT`·`NO_CONTEST`는 상태가 아니라 `FINISHED`가 싣는 결과 값이다. 상태 라벨은 일곱 그대로다.

### 2.4 자격 증명 — 부트스트랩·좌석 정체·회전·펜싱

이 절의 설계 원칙 하나: **정체(identity)는 안정적이고, 자격(credential)은 회전한다.** 인가·중복 제거·펜싱은 전부 정체에 붙이고, 자격은 정체를 증명하는 무기명 값일 뿐이다. 이전 판이 중복 제거 캐시 키를 좌석 토큰으로 잡아 회전 때마다 중복 제거가 무효화된 것이 이 구분을 놓친 결과다.

#### 2.4.1 부트스트랩 — 업그레이드 통로로 자격을 *발급*하는 문제

§1.8에서 확인했듯 업그레이드 단계는 "이미 아는 값을 제시"만 지원하고, 토큰 수는 정확히 2개로 고정돼 있다. 그러므로 **좌석 토큰은 업그레이드에서 발급할 수 없다.** 경계를 이렇게 나눈다.

| 단계 | 무엇이 오가는가 |
|---|---|
| ① WS 업그레이드 (`Sec-WebSocket-Protocol`) | `[digit-duel.v1, <입장 자격>]` — 기존 2토큰 형태를 그대로 쓴다. 서버는 공개 마커만 되돌린다(§1.8, 변경 없음). |
| ② 소켓 오픈 직후 서버의 첫 프레임 (인밴드) | 서버가 **좌석 토큰을 여기서 발급한다.** `room_opened` / `room_joined` / `room_resumed` 중 하나이며, §2.5.1의 봉투대로 **현재 `epoch`를 함께 싣는다** — 클라이언트가 다음 재개 자격에 넣을 값이 이것이다. |
| ③ 이후 모든 클라이언트 프레임 | 좌석 토큰과 `tokenGen`을 실어 보낸다(§2.5). |

**입장 자격**은 한 글자 종류 접두사 + 값이다. `-`와 영숫자는 RFC 7230 token 집합 안이므로(`server/security.js:121`) 별도 인코딩이 필요 없다.

| 형태 | 뜻 | 서버 동작 |
|---|---|---|
| `c-<nonce>` | 새 룸 생성 | 비밀값이 아니다. 클라이언트가 만든 임의 문자열이며 재시도 식별용일 뿐이다. 서버는 룸을 만들고 ②에서 초대 코드 + 좌석 0 토큰을 발급한다. |
| `j-<초대코드>` | 기존 룸 참가 | 코드를 상수시간 비교로 조회, 성공 시 코드를 즉시 무효화하고 ②에서 좌석 1 토큰을 발급한다. |
| `r-<에폭>.<좌석토큰>` | 기존 좌석 재개 | **에폭을 자격 안에 실어야 한다**(아래 2.4.1.1). 에폭을 먼저 대조하고, 통과할 때만 §2.4.3의 규칙으로 토큰을 검증한 뒤 ②에서 `room_resumed`를 보낸다. |

- **[추론]** `c-`는 비밀을 요구하지 않으므로 WAN에서 **누구나 룸을 만들 수 있다**. 이것을 숨기지 않고 그대로 적는다. 억제는 세 가지에 의존한다: 기존 IP별 업그레이드 토큰 버킷(`server/server.js:205-208`), 기존 연결 수 상한(`:231-234`), 그리고 신설하는 **전체 동시 룸 상한**(200, 제안 — 상한 도달 시 `E_CAPACITY`). 초기 지인 대상 규모에서는 이 정도가 균형점이라고 판단하며, 남용이 관측되면 생성 자격을 추가하는 것이 다음 단계다.
- **[권고]** 서버 전체 접근 코드(`ACCESS_CODE`)는 WAN 배포에서 **유지하지 않는다**. 매 기동마다 바뀌고 저장소에 없는 값(§1.8)은 LAN에서 운영자가 화면으로 읽어주는 전제였고, WAN에서는 그 전달 경로가 없다. 접근 통제는 룸 초대 코드 계층으로 옮긴다. LAN 실행 경로는 기존 동작을 그대로 둔다.

##### 2.4.1.1 재개 자격은 에폭을 함께 나른다 [권고]

§2.8은 "재개 요청의 `epoch`가 현재와 다르면 즉시 `E_EPOCH`"라고 규정하는데, 토큰만 실은 자격으로는 서버가 그 비교를 할 수 없다. 이전 판이 에폭 판정을 규정해 놓고 에폭을 나르는 통로를 정하지 않은 것이 그 구멍이다. 재개 자격을 **두 부분**으로 고정한다.

- 형식은 `r-<에폭>.<좌석토큰>`이다. `<에폭>`은 클라이언트가 **마지막으로 받은 서버 프레임의 `epoch`**(8자 소문자 16진, §2.5.1)이고 `<좌석토큰>`은 §2.4.3의 base64url 22자다.
- `.`과 `-`는 RFC 7230 token 집합 안이므로(`server/security.js:121`) 하위 프로토콜 통로를 그대로 탄다. 전체 길이는 `r-`(2) + 8 + `.`(1) + 22 = **33자**로 64자 상한(`server/security.js:119`) 아래다. 구분자 `.`은 base64url 문자 집합에도 16진 집합에도 없어 모호하게 갈라지지 않는다.
- 두 부분 중 하나라도 없거나 형식이 다르면 **업그레이드 단계에서 거절한다** — 현행 `rejectUpgrade` 경로를 그대로 쓰고 이유를 싣지 않는다(`server/server.js:194-200`). 업그레이드 이전에는 인밴드 오류 프레임을 보낼 소켓이 아직 없다. **에폭 없는 `r-`는 받지 않는다** — 받아 주면 §2.8의 판정을 우회하는 두 번째 경로가 생긴다.
- 형식이 맞으면 **업그레이드는 통과시키고**, 아래 판정 결과는 ②번 자리의 **인밴드 첫 프레임**으로 보낸 뒤 필요하면 소켓을 닫는다. 그래야 클라이언트가 `E_EPOCH`(무효 처리)와 `E_SEAT_TOKEN_INVALID`(재연결 실패)를 구분해 표시할 수 있다.
- 첫 연결(`c-`·`j-`)은 아직 볼 에폭이 없으므로 에폭을 싣지 않는다. 에폭은 ②번 프레임으로 처음 내려온다.

**판정 순서와 각 응답이 실제로 뜻하는 것**

| 제시된 에폭 | 서버 동작 | 클라이언트 표시 |
|---|---|---|
| 현재 에폭과 **다름** | **토큰을 검증하지 않는다.** 프로세스가 바뀌었으면 검증할 토큰 상태가 애초에 남아 있지 않다(§2.8 — 룸 상태는 인메모리, 프로세스 생애를 넘지 않는다). 유예 타이머와 무관하게 즉시 `E_EPOCH`. | "서버 재시작으로 경기가 무효 처리되었습니다" (`VOID` — 몰수패 아님) |
| 현재 에폭과 **같음** · 토큰이 그 좌석의 현재 토큰 또는 직전 토큰 | 정상 재개 (§2.4.3 · §2.4.4) | 재연결 완료 |
| 현재 에폭과 **같음** · 토큰이 맞지 않거나 폐기됨 | `E_SEAT_TOKEN_INVALID` | "재연결에 실패했습니다" |
| 현재 에폭과 **같음** · 룸이 이미 종료 | `E_ROOM_CLOSED` | 결과 화면 |

- **`E_EPOCH`는 "토큰이 유효했다"를 뜻하지 않는다.** 재시작 뒤에는 아무 문자열이나 넣어도 같은 `E_EPOCH`가 나온다. 서버가 **잃어버린 휘발성 토큰을 검증한 척하지 않기 위해** 이 응답에는 토큰에 관한 어떤 정보도 싣지 않으며, 유예 타이머도 참조하지 않는다.
- 반대로 `E_SEAT_TOKEN_INVALID`가 추가로 알려주는 사실은 "에폭이 같다"뿐이고, 그 값은 이미 모든 서버 프레임에 공개돼 있다(§2.5.1). 두 응답은 서로 구분되지만, 구분이 새로 흘리는 정보는 없다.
- 재개 실패 응답도 기존 업그레이드 토큰 버킷·`AttemptLimiter`의 적용을 그대로 받는다(예외 없음).


#### 2.4.2 좌석 정체 — 안정적인 축

- **좌석 정체 = `(roomId, seat)`**, `seat ∈ {0, 1}`. 룸 생애 동안 바뀌지 않는다.
- 아래 셋은 **전부 좌석 정체에 붙는다**: 인가 판정(§2.5.4), `requestId` 중복 제거(§2.5.3), 연결 펜싱(§2.4.4).
- 좌석 토큰은 "이 소켓이 저 좌석 정체다"를 증명하는 무기명 값이고, 회전해도 위 셋은 영향을 받지 않는다.

#### 2.4.3 좌석 토큰 — 회전과 ack 겹침

- 128비트 난수를 base64url(패딩 없음, 22자)로 인코딩한다. RFC 7230 token 집합 안이고 64자 상한(`server/security.js:119`) 아래다.
- **보관**: 탭의 JS 메모리 변수에만 둔다. URL·쿼리·쿠키·`localStorage`·`sessionStorage` 어디에도 쓰지 않는다 — 현행 `NET.code` 취급과 같은 원칙(§1.10).
- **따라서 새로고침하면 좌석을 잃는다.** 재개(`r-`)는 **같은 페이지 인스턴스가 살아 있는 동안의 네트워크 단절**에만 적용된다. 새로고침 후 복귀는 이 번들이 제안하지 않으며, 영속 저장을 도입하는 확장으로도 제안하지 않는다 — 필요해지면 별도 안건이다.
- **회전**: 재개가 **확인(ack)된 현재 토큰으로** 승인될 때만, 서버는 그 좌석에 새 토큰을 발급하고 `tokenGen`(좌석별 단조 증가 정수)을 1 올린다. 아직 확인되지 않은 회전이 떠 있는 동안에는 **다시 회전하지 않는다**(아래).
- **ack 겹침 — 회전 응답이 유실되는 경우**: 새 토큰을 실은 ②번 프레임이 유실되면 클라이언트는 구 토큰만 들고 있게 된다. 구 토큰을 즉시 폐기하면 그 좌석은 유예가 끝날 때까지 영구히 복귀할 수 없다. 그래서:
  - 서버는 좌석마다 **직전 토큰 하나를 함께 유효한 채로 둔다** (둘 이상은 두지 않는다).
  - 직전 토큰은 **`r-` 재개 용도로만** 받는다. §2.5의 일반 명령 인증에는 쓸 수 없다.
  - 클라이언트가 **현재 `tokenGen`을 실은 프레임을 한 번이라도 보내면** 서버는 그것을 수신 확인으로 보고 직전 토큰을 즉시 폐기한다. 그 순간 그 좌석은 "확인됨"이 된다.
  - **직전 토큰으로 재개하면 서버는 회전하지 않는다.** 이미 발급해 둔 **같은 토큰·같은 `tokenGen`을 그대로 다시 보낸다**(재전송이지 새 발급이 아니다). 바뀌는 것은 `connGen`뿐이며 그것만 1 오른다(§2.4.4).
  - 이 규칙이 없으면 다음이 난다: 회전 응답이 유실될 때마다 다시 회전하면 두 번째 유실 시점에 클라이언트가 든 토큰은 현재도 직전도 아니게 되고, 그 좌석은 **유예가 끝날 때까지 영구히 잠긴다**. 같은 토큰을 재전송하면 클라이언트가 든 토큰은 **언제나 현재 토큰 아니면 직전 토큰**이므로, 응답이 몇 번 유실되든 유예 안에서는 반드시 복구된다.
  - 따라서 유효 토큰은 항상 최대 2개로 유지되고, `tokenGen`은 응답 유실 횟수만큼 벌어지지 않는다.
- **폐기 시점**: ① 룸이 `CANCELED`/`VOID`/`CLOSED`로 갈 때 양 좌석 모두, ② 위 ack로 직전 토큰이 확정 폐기될 때, ③ 유예 만료로 그 좌석이 몰수/취소 처리될 때. 폐기된 토큰은 `E_SEAT_TOKEN_INVALID`.
- **재시도**: 클라이언트는 지수 백오프(1s → 2s → 4s → 최대 10s, 제안)로 `r-` 재개를 자동 재시도한다. 유예 만료가 상한 역할을 하므로 별도 횟수 제한은 두지 않는다. 재개 요청도 기존 업그레이드 토큰 버킷·`AttemptLimiter`의 적용을 그대로 받는다(예외 없음).

#### 2.4.4 연결 펜싱 — 중복 소켓과 재생(replay)

토큰 상태와 **무관하게** 결정되도록, 펜싱은 좌석 정체에 붙은 카운터로 한다.

- 좌석마다 `connGen`(단조 증가 정수)을 둔다. 생성·참가·재개로 연결이 **승인될 때마다** 1 올리고, 승인된 소켓에 그 값을 도장처럼 찍는다.
- 승인 시점에 그 좌석의 이전 소켓이 아직 열려 있으면 서버가 능동적으로 닫는다(`E_SUPERSEDED`).
- 이후 들어오는 프레임은 **소켓 도장 = 현재 `connGen`**일 때만 처리한다. 낮으면 처리하지 않고 그 소켓을 닫는다.
- **[추론]** 이렇게 두면 탈취된 구 토큰으로 새 소켓을 붙이더라도 정상 클라이언트가 다시 재개하는 순간 `connGen`이 올라가 공격 소켓이 즉시 무력화된다. 두 소켓이 동시에 같은 좌석의 명령을 적용하는 창은 남지 않는다. 이것은 탈취 자체를 막는 장치가 아니라 **동시 사용 창을 없애는** 장치다.

#### 2.5.2 `revision`과 `seq` — 서로 다른 두 검사
- **`revision`** (룸 단위, 단조 증가): "판이 언제 바뀌었나". 클라이언트는 행동을 결정한 시점의 값을 `baseRevision`으로 싣는다. `baseRevision !== room.revision`이면 서버는 **행동을 적용하지 않고** `E_STALE_REVISION`으로 거부한 뒤 최신 좌석 뷰를 다시 보낸다.
- **`seq`** (좌석별 발신 순번, 단조 증가): "내가 보낸 프레임을 다 받았나". 클라이언트가 `seq` 건너뜀을 감지하면 `{"t":"resync"}`를 보내고, 서버는 전체 좌석 뷰 스냅샷으로 답한다. WebSocket은 순서를 보장하지만 유실·재개 경계에서는 누락이 가능하므로, 델타만으로 상태를 재구성하는 경로에 이 검사가 필요하다.
- 두 값은 독립이다. `revision`은 판정 정합성, `seq`는 전송 정합성을 본다.

#### 2.5.3 `requestId` 중복 제거 — 회전에도 살아남는 키
- 캐시 키는 **`(roomId, seat, requestId)`**다. **좌석 토큰을 키에 넣지 않는다** — 토큰은 §2.4.3대로 회전하므로, 토큰을 키로 삼으면 회전 직후 같은 `requestId` 재전송이 새 요청으로 취급돼 중복 적용된다.
- TTL 120초(제안).
- 같은 키가 다시 오면 **행동을 다시 실행하지 않는다**. 이것이 단순 캐시가 아닌 이유: RNG를 다시 굴리지 않고, HP·좌표·ready를 다시 바꾸지 않으며, `revision`도 올리지 않는다. 최초 처리 때 저장한 응답을 그대로 다시 보낸다(`seq`만 새로 채번한다).
- 다른 좌석에서 같은 `requestId` 문자열이 와도 키가 다르므로 별개 요청이다.

#### 2.5.4 인가 — `S.current` 하나로는 부족하다 (§1.5)

서버는 §1.5의 `netActor()`를 규칙 모듈에서 그대로 재사용해 **행위자 좌석**을 계산하고, 요청 좌석과 비교한다. 여기에 **소유권 검사**를 더한다.

| 액션 종류 | 요구하는 행위자 | 추가 소유권 검사 | 근거 |
|---|---|---|---|
| 배치(`setup`·`ready`·`unready`) | **요청 좌석 자신** — 단일 차례 포인터(`setupPlayer`)를 게이트로 두지 않는다(아래) | 대상 유닛·로스터가 요청 좌석 소유 | `demo/index.html:2099-2101`(온라인은 좌석별 `NET.mySetup` 독립 캡처), `:2104`(`S.setupPlayer` 교대는 핫시트 전용) |
| 일반 이동·전투 개시 | `room.current` | 움직이는 말이 요청 좌석 소유 | `demo/index.html:4957` |
| 전투 중 행동(기술·아이템·도망·넘기기) | `actorOfPhase()` 측 전투원의 소유자 | 해당 전투원이 요청 좌석 소유 | `demo/index.html:4954`, `:2942-2948` |
| 도망 후 교환 선택(`fleeSwap`·`fleeSkip`) | `room.fleePick.owner` — **현재 턴 좌석이 아닐 수 있다** | 후보가 `fleePick.cands`에 있고 요청 좌석 소유 | `demo/index.html:4955`, `:1271`, `:4991-4992` |
| 기권(`resign`) | **`room.current`** (행위자 아님 — 코드상 예외) | 없음 | `demo/index.html:4967` |

- **`netActor()`의 `setup` 분기는 서버로 옮기지 않는다.** `S.setupPlayer`는 **한 기기에서 두 사람이 번갈아 배치하는 핫시트 교대 포인터**이며(`demo/index.html:4953`이 `setup` 단계에서 그것을 돌려주고, `:2104`가 좌석 0 완료 시 `S.setupPlayer=1`로 넘기며 `handoff()`로 화면을 넘긴다), 온라인 경로는 애초에 그 교대를 타지 않는다 — 각자 자기 화면에서 로스터·배치를 끝내고 `NET.mySetup`으로 캡처한 뒤 접속한다(`:2099-2101`). 서버 권위에서 `room.setupPlayer`를 배치 명령의 행위자 게이트로 쓰면, **두 좌석이 동시에 준비하는 §2.3의 SETUP 규칙과 정면으로 어긋나** 한 좌석이 상대의 차례를 기다려야 한다.
- 따라서 `SETUP`의 인가 규칙은 하나다: **인증된 각 좌석은 언제든 자기 `setup`·`ready`·`unready`만 바꿀 수 있고, 상대 좌석의 배치·ready는 어떤 명령으로도 바꿀 수 없다.** 순서 제약은 없다. 이는 §2.3의 SETUP 행("`setup`(자기 배치 갱신)")·READY 단일 규칙("그 좌석이 자기 배치를 바꿀 때만 자기 ready가 false")과 같은 문장이며, 상대 소유 유닛을 지정한 `setup`은 `E_NOT_OWNER`다.
- 행위자 불일치 → `E_NOT_ACTOR`. 소유권 불일치 → `E_NOT_OWNER`. 두 코드를 분리하는 이유는 클라이언트 버그와 조작 시도를 로그에서 구분하기 위함이다.
- `fleePick`에는 토큰이 이미 있다(`S.fleePick.token = turnCount + ":" + battlesUsed + ":" + pieceId`, `demo/index.html:3748`)고 확인된다. 서버도 이 토큰을 받아 대조해 **지나간 선택 창의 늦은 입력**을 거부한다(`demo/index.html:4973-4974`가 클라이언트에서 하는 검사와 같은 것을 서버에서 한다).

### 2.6 좌석별 필드 화이트리스트

§1.4의 세 등급을 그대로 데이터 규칙으로 옮긴다. **기본은 "보내지 않는다"이고, 이 표에 있는 것만 보낸다.**

#### 2.6.1 유닛 필드는 (좌석 관계 × 문맥)별 열거다 — "전체 레코드"는 없다 [권고]

`revealed`를 "전체 레코드 공개"로 읽으면 새는 것이 있다. `mkPiece()`가 만드는 레코드에는 화면에 한 번도 그려지지 않는 내부 필드가 함께 들어 있고(`demo/index.html:1299-1309`), 기술은 `revealed`와 **다른 축**으로 열린다(`:1302`의 `revealedSkills`, `:2989-2992`). 그래서 등급이 아니라 **좌석 관계별로 필드를 열거**하고, **열거에 없는 키는 등급과 무관하게 나가지 않는다**(기본값 "보내지 않는다").

| 필드군 | 자기 좌석 (`owner===seat`) | 공개된 상대 (`revealed`) | 미공개 상대 (등급 B) |
|---|---|---|---|
| 존재·위치 `id`(별칭)·`r`·`c`·`owner`·`alive`·`immobile` | 보낸다 | 보낸다 | 보낸다 |

| 포획 `cap` | 보낸다 | **안 보낸다** — 포획된 하수인의 정체는 별도 공개 사건이다 | **안 보낸다** |

- **등급 판정이 필드 열거보다 먼저다.** `visibleTo()`는 `revealed`를 보지 않는다(`demo/index.html:1361-1366`). 그러므로 **`revealed===true`인 말이라도 숲 안에 있고 인접 관측자·`tempReveal`이 없으면 등급 A**이고, 레코드 자체가 배열에서 빠진다. "공개된 말은 항상 보인다"가 아니다.
- **자기 좌석도 객체를 통째로 넘기지 않는다.** 서버 내부 정수 `id`와 서버 전용 부기(난수 상태·타이머 핸들·소켓 참조)는 어느 좌석에도 나가지 않는다. 열거 방식을 쓰는 실익이 여기서도 남는다 — 레코드에 필드가 새로 생겨도 자동으로 새지 않는다.

#### 2.6.2 기술 공개는 `revealed`가 아니라 `revealedSkills`다 [권고]

- `revealedSkills`는 **기술 인덱스의 배열**이고 `revealed`와 독립이다(초기값 `null`, `demo/index.html:1302`). 전투 패널은 `viewer===2 || piece.owner===viewer || (pf.revealedSkills && pf.revealedSkills.includes(i))`일 때만 기술 이름과 쿨을 그리고, 아니면 **종류(kind)만** `?${SKIND_KO[sk2.kind]}`로 그린다(`:2989-2992`).
- 서버도 같게 보낸다: 상대 전투원의 기술 배열은 **인덱스마다** `{i, revealed:true, id, name, cd}` 또는 `{i, revealed:false, kind}` **둘 중 하나만** 싣는다. `revealed:false` 항목에 `id`·`name`·`cd`를 실어 보내고 클라이언트에서 가리는 방식은 **금지한다** — 그것이 정확히 §1.3이 지적한 현행 노출이다.
- 이 문맥은 **전투 중 두 전투원에 한정**된다. 보드 뷰의 상대 말에는 `revealed`가 참이어도 `skills`를 아예 보내지 않는다. 현행 보드 렌더도 기술을 그리지 않는다(`:1716-1717`은 `pcBodyHtml(p)`만 부른다).
- 전투 중 두 전투원의 `hp`·`maxHp`·`shield`와 상태 아이콘(`burn`·`weaken`·`shock`·`dmgCut`·`focusCharge`·`vulnMark`)은 **그 전투 동안 양쪽 좌석에 공개된다**(`:2984-2988`, `stIcons()` `:3556-3558`). 이는 전투 문맥 한정 공개이며 §2.6.1의 보드 뷰 열거로 새지 않는다 — 전투가 끝나면 그 필드들은 다시 나가지 않는다.
- 전투에 나오지 않은 말의 `revealedSkills`는 어떤 문맥에서도 상대에게 나가지 않는다. "몇 개가 공개됐는가"라는 개수도 보내지 않는다.

**[권고]** §2.6의 표와 §2.6.1·§2.6.2의 열거는 체크리스트다. §2.2의 규칙 모듈에서 "룸 상태 → 좌석 뷰" 변환 함수는 단일 지점이어야 하고, 그 함수의 테스트는 ① **등급 A 유닛의 레코드가 결과에 존재하지 않는다** ② **어떤 유닛 레코드도 §2.6.1 열거에 없는 키를 갖지 않는다**(키 집합 차집합이 공집합) ③ **`revealedSkills`에 없는 인덱스의 기술에 `id`·`name`·`cd`가 붙지 않는다** 를 각각 **레코드 구조로** 검증해야 한다(§3 A1·A6·A7).

### 2.8 재시작·크래시·롤백 — 규칙 하나

이전 판은 "정상 드레인은 통지 후 VOID", "비정상 크래시는 유예 후 VOID", "구 프로세스는 자기 소켓을 계속 소유", "신규 연결은 새 프로세스로" 를 동시에 적었다. 그러면 **드레인 중인 룸의 좌석이 끊겼다가 재접속할 때 새 프로세스로 라우팅돼, 구 프로세스가 멀쩡히 살아 있는데도 에폭 불일치로 VOID가 된다.** 두 정책이 같은 사건에 다른 답을 낸다.

**단일 규칙으로 대체한다.**

- 서버 프로세스는 기동 시 난수 `epoch`를 만들고 모든 서버 프레임에 싣는다. 클라이언트는 마지막으로 본 `epoch`를 기억한다.
- **룸 상태는 인메모리이며 프로세스 생애를 넘지 않는다. 프로세스가 바뀌면 살아 있던 모든 룸은 `VOID`다.** 계획된 재시작이든 크래시든 결과가 같다. 차이는 **사전 통지가 가능했는가뿐**이다.
- 재개(`r-<에폭>.<좌석토큰>`, §2.4.1.1) 요청의 에폭이 현재와 다르면 **토큰을 검증하지 않고** 유예 타이머도 기다리지 않고 즉시 `E_EPOCH`를 돌려주고, 클라이언트는 "서버 재시작으로 경기가 무효 처리되었습니다"로 표시한다. **몰수패가 아니다** — 플레이어 귀책이 아니기 때문이다.
- `epoch`가 같은데 룸·좌석을 못 찾으면 그냥 오류다(`E_ROOM_CLOSED` / `E_SEAT_TOKEN_INVALID`). 무효도 몰수도 아니다 — 애초에 유효한 재개가 아니었다.
- **두 타이머는 별개다.** 이탈 유예(60초, 제안)는 소켓이 끊긴 순간부터 돈다. 에폭 불일치는 재시작 시점에 이미 확정돼 있으므로 타이머와 무관하게 즉시 처리한다.

**계획된 재시작 절차 (제안)**
1. 모든 `IN_PROGRESS` 룸에 `server_notice`로 예고(5분, 제안)를 방송한다. 이 시점부터 새 룸 생성을 `E_CAPACITY`가 아닌 `E_DRAINING`으로 거부한다.
2. 예고 시간 동안 진행 중 경기가 자연 종료되기를 기다린다.
3. 예고가 끝나면 남은 룸을 `VOID`로 정리하고 프로세스를 교체한다. 짧은 무중단 공백이 발생하며, **이를 없애려 하지 않는다.**

**블루/그린·무중단 배포는 이 번들에서 제안하지 않는다.** WebSocket은 TCP 연결이라 프로세스 간 이관이 불가능하고, 두 프로세스를 동시에 띄우면 재접속을 소유 프로세스로 되돌리는 고정(sticky) 라우팅이 필요해진다. 그 복잡도는 룸 상태를 외부 저장소로 뺀 뒤에 의미가 있으므로 §2.7의 2단계로 미룬다.

**롤백**: 이전 빌드를 다시 배포해 위 절차로 재시작한다. **진행 중이던 경기는 복구되지 않는다** — 롤백 이후 새로 생성되는 룸만 이전 빌드로 서비스된다. 배포가 헬스체크(§2.1)에서 실패해 아직 교체하지 않았다면, 기존 프로세스는 영향을 받지 않고 진행 중 경기도 끊기지 않는다.

### 2.10 이 번들에 넣지 않은 것

- **퀵매칭** — 비공개 룸을 일정 기간(2주, 제안) 운영해 §2.9 실측을 얻은 뒤 별도 안건으로 제안한다. 착수 기준 수치를 지금 정하지 않는다. 실측이 없는 상태에서 정한 목표치는 근거가 아니기 때문이다.
- 계정 시스템, 공개 방 목록, 호스트 이전(방장 위임), 관전.
- 새로고침 후 좌석 복귀(§2.4.3).
- 무중단 배포·수평 확장(§2.8, §2.7).

## 5. 이 설계가 확정하지 않는 것 (명시)

- **작업량 추정을 하지 않았다.** §2.2의 규칙 모듈 분리 규모를 코드로 실측하지 않았으므로, 일정·공수를 제시하지 않는다.
- **§2의 모든 수치는 (제안)이다.** 실측 근거가 없다.
- **성능·용량 주장을 하지 않았다.** §2.9의 임계값은 관측 시작점이지 보장이 아니다.
- **보안 보장을 주장하지 않는다.** §2.4.4는 "동시 사용 창을 없앤다"이지 "토큰 탈취를 막는다"가 아니다. §2.6은 "서버가 보내지 않는다"이지 "클라이언트가 안전하다"가 아니다.
- **CJ 승인·Saturn QA 통과를 주장하지 않는다.** 이 문서는 제안이며, 검토받은 바 없다.

## 6. 참고 — 외부 기술 주장의 1차 출처

이 문서에서 실제로 근거로 쓴 것만 단다.

- WebSocket 프로토콜 — 하위 프로토콜 협상(`Sec-WebSocket-Protocol`)·Origin 헤더·`wss` 스킴 정의. §1.8·§2.4.1의 통로 제약이 따르는 규격: RFC 6455 — https://www.rfc-editor.org/rfc/rfc6455
- HTTP/1.1 메시지 문법 — 하위 프로토콜 토큰의 문자 집합(`server/security.js:121`이 구현하는 token 규칙): RFC 7230 — https://www.rfc-editor.org/rfc/rfc7230
- TLS 1.3 — `wss://` 종단의 기반 규격. 이 문서는 강제 버전을 규정하지 않고 리버스 프록시의 최신 안전 기본값을 전제한다: RFC 8446 — https://www.rfc-editor.org/rfc/rfc8446
- WebSocket은 브라우저 동일 출처 정책의 보호를 받지 않아 서버가 Origin을 직접 검증해야 한다는 권고(현행 `isSameOrigin` 검사의 근거): OWASP HTML5 Security Cheat Sheet, WebSockets 절 — https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html
- 세션 토큰을 URL·쿼리·로그에 싣지 않는다는 원칙(§2.4.3 좌석 토큰 보관 규칙): OWASP Session Management Cheat Sheet — https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html
