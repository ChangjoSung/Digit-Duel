**현행 CJ 지시(2026-10-02 · 구현 중 최종 정정):** 내 배틀 스킬은 **미해금 소개를 포함해 기존 하수인 정보의 스킬 설명을 그대로 재사용**한다. 실제 행동은 해금된 활성 슬롯만 가능하다. **상대 스킬은 공개 여부와 무관하게 어디에도 표시하지 않는다.** 상대 실제 출전 개체의 등급·이름·HP·방어막·기본 6스탯·디버프를 표시하며 `?` 자리 표시를 두지 않는다. 현재 전투원의 등급은 대리 출전도 전투 한정 공개한다. **별도의 위력 범위 표시는 삭제**하며, 기존 설명의 수치 문구는 유지한다. #293/#294/#295 UI를 재사용하고 불필요한 텍스트를 넣지 않는다. 아래 초기 보고의 위력 표시·상대 사용 기술 표시·대리 등급 은닉 및 직전 PD의 내 미해금 소개행 철회 해석은 이 지시로 대체된다. `0~0` 분석은 삭제할 표시의 과거 원인 기록이며 현행 재현 AC가 아니다. 구현 근거는 [최신 CJ 원문](../references/CJ_COMMENT.md)과 Venus 현행 계약을 따른다.

## 판정

CJ 콘티를 배틀 화면의 새 배치 기준으로 적용하는 안을 권고한다. #293의 실제 개체 값·시너지 표시 원칙과 #294의 하수인 정보·스킬 소개 형식을 재사용한다. 배틀 패널은 **HP/현재 방어막 한 줄 + 기본 6스탯 두 줄(3열×2행)**이다. #294 도움말의 8스탯 4열×2행을 그대로 옮기지 않는다.

온라인 `0~0`으로 이어지는 공통 원인은 정적으로 확인했다. 공격력을 생략한 서버 뷰와 불완전한 클라이언트 복원, 누락을 0으로 바꾸는 계산이 연결된다. 전설 하나에 기본 공격력을 덧대는 수정으로는 등급 성장·가방 대리 출전까지 해결하지 못한다. 서버의 **현재 전투원 값**을 표시 원천으로 삼아야 한다.

이 보고는 구현 전 분석이다. 제품·테스트·설정 변경, 실행 재현, 정식 QA, 배포는 수행하지 않았다. CJ 제보 장면의 모드·전투원은 확인되지 않았으므로 발견한 경로가 그 장면과 동일하다는 것은 아직 추론이다.

## ‘상대도 공개’의 범위와 영향

화살표가 상대 정보 패널 전체를 가리키므로 **지금 싸우며 공개된 상대 전투원의 기본 6스탯까지 공개**하는 좁은 안(P1)을 권고한다. 단순히 패널 틀이나 HP만 다시 그리는 안(P0)은 이번 명시적 지시를 충분히 반영하지 못한다. 시너지·일시 버프를 포함한 유효 수치 전체 공개(P2)는 콘티에 근거가 없고 상대 편성 집계를 역산하게 한다.

P1도 정보 범위의 변경이다. 방어·속도 등으로 상대 동료 역할을 사용한 기술 이전에 알아볼 수 있으며, 대리 출전 개체의 성장 정도도 추론할 수 있다. ‘UI만 바꾸므로 공개 정보는 완전히 동일하다’고 보고해서는 안 된다. **최신 CJ ‘상대도 공개’ 지시를 이 전투 한정 6스탯 공개로 해석했다**는 내용과 이 영향을 구현 착수 시 GDD·프로토콜·경계 단언에 함께 반영해야 한다.

상대의 미공개 개체·미사용 기술/슬롯 수·인벤토리·시너지 편성 집계·개인 시너지 수치·시작 방어막 비율/층별 출처·내부 상태·상대 행동 시계는 계속 비공개다. 보드 상대 뷰에 6스탯을 추가하지 않는다. 전투 뷰에 `uid`·대리 출전 `grade`·전체 `syn*`를 편의상 싣지 않는다. 상대 공개 범위를 이보다 넓히려면 별도 CJ 지시가 필요하다.

## `0~0`의 공통 원인과 표시 계약

정적 경로는 `room.js:_serializeBattle` → `network.js:netSynthFighter` → `ui.js:battleModal` → `data.js:effAtk/slotPow` → `core.js:dmgRange`다. 현재 전투 뷰는 `atk`를 생략한다. 클라이언트는 일반 종의 1등급 표, 왕/동료 상수, 구형 cap/reserve에서만 공격력을 복원한다.

| 조건 | 현재 경로에서 발생하는 문제 |
|---|---|
| 온라인 전설 본체 | 서버의 `L-*` 식별자는 일반 `ROSTER`에 없어 공격력 복원 실패 → `undefined` → `effAtk`의 `\|\|0` → `0~0`. |
| 온라인 경제 가방 대리 출전 | 복원이 가방 개체를 찾지 않아 같은 누락 경로로 연결된다. 종만으로는 같은 종·다른 등급 개체를 특정할 수 없다. |
| 온라인 일반 하수인 2~4등급 본체 | 공격력을 1등급 표에서 읽어 0이 아니어도 위력이 낮게 잘못 표시될 수 있다. |
| 상대 공개 기술의 대리 출전 | 복원 불가를 `?`로 표시하려는 주석과 달리 누락이 0으로 바뀌는 경로가 있다. P1에서도 서버가 보낸 기본 공격력만 소비하고 상대 시너지는 제외한다. |
| 오프라인 | 실제 개체를 직접 읽으므로 이 직렬화 누락 경로는 해당하지 않는다. 제보가 오프라인이었다면 별도 재현에서 다른 원인을 확인해야 한다. |

공개 방의 실제 피해는 서버 Core가 실제 전투원으로 계산하고, 클라이언트는 행동 의도만 전송한다. 직렬화 결과나 위력 표시 값이 서버 판정으로 되돌아가는 경로는 없다. 따라서 **발견한 누락 경로 자체는 표시 문제**라는 정적 근거가 있다. CJ 제보 경기의 실제 피해까지 실행 대조한 것은 아니다.

수정은 데이터 원천과 표시 경계에서 한다. 서버는 실제 전투원 `atk·def·spd·dodge·crit·statusPct`를 양쪽 전투 뷰에 허용하고, 클라이언트는 그 값을 직접 소비한다. 누락/비유한 값은 `?` 또는 확인 불가로 표시하며 정상 숫자 0은 그대로 둔다. 세 위력 표시 호출을 공통 UI 경계로 처리하고, 판정 공용 `effAtk`를 표시 문제 때문에 변경하지 않는다.

현재 `dmgRange(slotPow(...))`는 상대 방어·상성·치명·방어막 흡수까지 반영한 최종 HP 피해가 아니다. 화면 이름은 **‘위력’**으로 명확히 하고 대상·효과 설명을 함께 표시한다. 이는 #296의 ‘예상 피해’를 방어 전 위력 범위로 명확히 정의하는 권고이며, 순수 HP 감소량 예측 AC까지 충족했다고 주장할 수 없다. 실제 HP 감소량 예측이 필요하다면 계산 범위와 상대 정보 노출을 먼저 별도 정의해야 한다. 이번 안에서는 별도 전투 계산기나 피해 식 사본을 만들지 않는다. 비피해 기술에는 효과를 표시하며, 합법적인 0 위력·반올림·회피·완전 흡수와 데이터 누락을 구분한다. 모든 `0~0`을 오류로 판정하거나 숫자를 임의로 높이지 않는다.

## 함께 수정해야 하는 표시 경로

`v2ReqOk`는 `onceUsed`와 `burrowRound`를 읽지만 온라인 전투 뷰에는 두 값이 없다. 전투당 1회 사용 후에도 사용 가능으로 보이거나 잠복 다음 라운드 기술이 불가로 보일 수 있는 정적 경로가 확인됐다. #296의 ‘사용 가능 상태’ AC에 포함한다. 서버의 기존 `slotUsable` 결과를 **내 활성 슬롯에만** 전달하고 버튼·불가 안내·수동 턴 종료가 같은 결과를 사용하게 한다. 내부 상태 배열을 공개하거나 클라이언트에 규칙을 복사하지 않는다.

시너지 칩은 기존 전투 시작 시점의 `ownSyn` 스냅샷과 Core selector를 사용한다. 왕국은 현재 전투원의 속성/용 효과, 개인 효과는 **현재 출전 전설**에 한정한다. 보드 전체 전설을 나열하는 `synExtraView`를 그대로 붙이면 다른 개체의 개인 효과를 이 전투원에게 적용된 것처럼 보일 수 있다. 시너지 스냅샷이 없으면 현재 보드로 추정해 0을 만들지 않는다.

부서 초안의 ‘동료 공격력도 18/14로 복원해야 한다’는 가설은 채택하지 않는다. `ALLY_BASE` 표는 18/14지만 `mkPiece`의 16을 `applyFixedStats`가 덮어쓰지 않아 현재 엔진은 두 동료 모두 16을 사용한다. 표와 엔진의 불일치는 별도 기획 확인 사항으로 기록하고, #296에서는 엔진 값을 표시하며 수치/판정을 바꾸지 않는다. 미해금 소개행 생략·8스탯 배틀 패널·모든 양수 기술의 0 표기를 오류로 간주하는 초안 제안도 채택하지 않는다.

## 실행 설정·산출물·보존

Mercury의 현재 turn context는 `gpt-6.1-sol / xhigh`이며 실행 인수에 `service_tier=fast`가 있다. API의 최종 처리 우선순위는 이 환경에 별도로 노출되지 않는다. 최초 인수 턴은 `workspace-write/on-request`였으나 이번 실행 턴의 환경은 **`danger-full-access / never`**다. 요청한 permission access와 다르며, PD가 자동 확대하거나 설정 파일을 변경한 결과가 아니다. 프로젝트/계정 기본값과 Worker 계약은 변경하지 않았다.
