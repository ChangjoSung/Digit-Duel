1. 두 문장 정의

Creat2ve Vibe Coding Structure는 한 명의 결정권자(CJ)가 자연어 코멘트만으로 다중 AI Agent 부서를 운영하는 개발 조직 체계다. 프롬프트를 복사해 붙이는 대신, 저장소의 CLAUDE.md 계약과 부서 자동화가 “코멘트 → 분석 → 승인 → 구현 → 교차 QA → 기록”의 전체 사이클을 굴린다.

이 핸드북에서 Agent는 Claude Code나 Codex 같은 코딩 AI의 한 세션을, 부서는 그 세션에 부여한 역할을 뜻한다. 부서는 사람이 아니라 역할이며, 필요할 때 켜지고 끝나면 꺼진다.

2. 왜 존재하는가

1인 개발자가 AI와 일할 때 무너지는 지점은 코딩이 아니라 운영이다. 이슈가 꼬리를 물고, 기획서 갱신이 누락되고, 세션이 바뀌면 맥락이 사라진다. 코드를 짜는 속도는 빨라졌는데 “지금 무엇이 결정되었고 무엇이 남았는가”를 아는 사람이 없어지는 것이다.

이 구조는 그 운영을 통째로 부서에 위임한다. 사람이 남기는 것은 결정과 실플레이 QA뿐이고, 나머지는 문서가 기억하고 Agent가 집행한다. 핵심 설계 사상은 여덟 줄로 요약된다.

  1. CJ Comment가 유일한 입력(런처)이다. 프롬프트 복사는 필요 없다.
  2. 세션은 소모품, 문서가 기억이다. 기억은 CLAUDE.md·이슈·Notion·스냅샷에 남긴다.
  3. Claude = 생성(기획·코드), Codex = 관리·검증(PD·QA·구성). 만든 모델과 검증하는 모델을 분리한다.
  4. 이벤트 구동: 요청이 있을 때만 부서 Worker가 기동하고, 끝나면 사라진다.
  5. 결정 전 구현 금지. 확정/추론/[기획 필요]를 모든 문서와 보고에서 구분한다.
  6. Worker는 git 쓰기 금지. 검증을 통과한 뒤 Coordinator(또는 PD)가 커밋한다.
  7. 문서는 누적이 아니라 치환한다. 새 내용을 넣을 때 낡은 내용을 지운다.
  8. 역할이 먼저, 모델은 나중. 작업의 영역·역할을 정한 뒤 provider를 붙인다. provider가 바쁘다고 다른 역할이 대신하지 않는다 — 같은 역할을 하나 더 띄운다(Role_1, Role_2).

비유 — 소방서. 소방관은 상시 순찰하지 않는다. 신고(CJ Comment)가 들어오면 출동하고, 상황이 끝나면 보고서를 남기고 복귀한다. 이 구조의 부서 Agent도 같다. 출동 기록(이슈·Notion)이 남기 때문에 다음 출동 팀이 무엇이 있었는지 안다.

배치 원칙. Claude = 생성(기획·코드), Codex = 관리·검증(PD·QA·구성). 같은 모델이 만들고 검증하면 같은 실수를 같이 놓친다 — Saturn이 그 동종 편향을 제거한다. 단, 이것은 역할에 provider를 붙이는 규칙이지 provider로 역할을 고르는 규칙이 아니다: 배치는 언제나 영역·역할이 먼저이고 provider는 그 역할의 실행기일 뿐이다 (역할 계약, rev 6).

역할 계약 — 역할이 먼저, 모델은 나중 rev 6 · 불변

부서 이름은 역할이고, Claude Code나 Codex는 그 역할을 실행하는 실행기(provider)다. 이 순서가 뒤집히면 “지금 비어 있는 Claude 세션이 Venus니까 Venus가 코드를 고치자”가 된다. rev 6은 그 뒤집힘을 실제로 겪은 뒤 계약으로 못 박았다. 역할이 먼저, 모델은 나중. 작업의 영역(area)과 역할(role)을 먼저 정하고, provider(Claude Code·Codex)는 그 역할을 실행하는 실행기일 뿐이다. provider가 바쁘거나 비어 있다는 이유로 다른 역할이 그 일을 대신하지 않는다 — 같은 역할을 하나 더 띄우거나(Role_2) 기다린다.

배치 순서

  1. 영역(area)과 역할(required_role)을 정한다 — CJ Comment의 내용만 보고, 어떤 세션이 비어 있는지는 보지 않는다
  2. 인스턴스 이름을 정한다 — 그 역할이 하나면 기본 이름(Mars), 이미 돌고 있으면 다음 접미사(Mars_2)
  3. 그 역할의 provider로 기동한다 — provider가 없거나 바쁘면 같은 역할을 추가하거나 기다린다. 앞 두 단계를 되돌리지 않는다

provider는 실행기다. 같은 provider(예: Claude Code)를 쓰는 다른 역할이 놀고 있어도 그 역할로 일을 넘기지 않는다(교차 역할 대체 금지). Venus와 Mars가 같은 Claude Code여도 Venus는 구현하지 않는다.

  • 인스턴스를 할당하기 전에 바쁜 집합 전체를 검사한다 — 할당 대상 역할뿐 아니라 다른 역할의 항목도 포함해서, 같은 이름 중복(Venus·Venus, Mars_1·Mars_1)이나 기본 이름과 Role_1 동시 존재(두 인스턴스가 index 1을 주장)가 하나라도 있으면 role_scope_mismatch로 멈추고 슬롯을 내주지 않는다.

dispatch preflight — 기동 전 다섯 필드

모든 dispatch는 required_role · mode · area · mutation · instance_index 를 갖추고 아래를 통과해야 한다. 하나라도 어긋나면 dispatch를 만들지 않고 role_scope_mismatch와 사유를 돌려준다.

  1. required_role이 역할 계약의 역할 중 하나다
  2. mode가 그 역할의 허용 mode 안에 있다 (Venus=PLAN, Mars·Jupiter·Earth=IMPLEMENT, Saturn=QA, Mercury=COORDINATE)
  3. area가 그 역할의 허용 area 안에 있다 — 역할 우선 라우팅 표와 일치
  4. mutation이 그 역할의 허용 집합 안에 있다 (Venus: none·docs / Saturn: none / Mercury: none·docs·metadata / Mars·Jupiter: none·docs·code / Earth: none·docs·assets)
  5. instance_index가 null(단일) 또는 1 이상의 정수이고, 인스턴스 이름이 Role 또는 Role_n 형식으로 일치한다
  6. provider가 적혀 있으면 그 역할의 provider와 같다 — 다른 provider나 다른 역할의 빈 슬롯은 근거가 되지 않는다

비유 — 회계 감사. 회사 재무팀이 장부를 만들고, 외부 감사인이 검증한다. 같은 팀이 만들고 검증하면 같은 가정을 같이 믿는다. Saturn이 다른 모델(Codex)인 이유가 정확히 이것이다. 감사인은 “재무팀이 맞다고 했다”를 근거로 삼지 않고 직접 장부를 다시 센다. Saturn도 구현자의 보고를 믿지 않고 기획서의 수용 기준(AC)과 헤드리스 테스트로 다시 확인한다.

4. 작동 원리 — 10단계와 패스트트랙

CJ Comment가 들어오면 PD가 먼저 갈림길을 판단한다. 복합 피드백·신규 기획 = 10단계 풀 사이클. 단순 지시(명확한 단일 변경) = 패스트트랙(1~6 생략: 구현 → QA → 보고).

풀 사이클 10단계

  1. MercuryCJ Comment를 안건별로 분류하고 영역·역할 기준으로 어느 역할이 1차 분석할지 판단 (provider 가용성은 판단 근거가 아니다)
  2. Venus기획 소관 안건 → Venus에 분석 요청
  3. Earth아트 소관 안건 → Earth에 분석 요청
  4. Mars / Jupiter개발 소관 안건 → Client·HTML·Unity·툴링은 Mars, Server는 Jupiter에 분석 요청
  5. Mercury부서 분석 보고를 취합해 CJ에 1차 보고
  6. CJ검토 — OK 또는 재작성 (재작성은 해당 부서만 다시)
  7. Mars / Jupiter / Earth전체 OK 시 역할별 병렬 구현 시작 — Client·HTML·Unity·툴링은 Mars, Server는 Jupiter, 아트는 Earth. 같은 역할이 둘 이상이면 Mars_1·Mars_2처럼 접미사로 병렬화. Venus는 구현하지 않고 PD는 취합만
  8. Saturn코드 구현물은 Saturn(Codex)이 교차 QA — PASS/REVISE/BLOCKED
  9. Mercury구현 보고서 취합 → CJ 보고
  10. CJ → MercuryCJ 플레이 QA 최종 승인 → PD가 GitHub·Notion·문서 최신화·정리

패스트트랙

  1. Mercury단순 지시로 분류 (명확한 단일 변경, 기획 판단 불필요)
  2. Mars / Jupiter / Earth역할 라우팅에 따라 구현 Worker 기동 — Client·HTML·Unity·툴링은 Mars, Server는 Jupiter, 아트는 Earth. 문구 하나짜리 변경이어도 Venus·Saturn·Mercury가 대신 구현하지 않는다
  3. Saturn교차 QA
  4. Mercury완료 보고 → CJ 묵시적/명시적 승인 → 이슈 종결·문서 정리

모든 부서는 Clear(세션 종료) 전에 자기 작업을 GitHub 이슈와 Notion에 기록한다. 부서 Agent는 작업마다 새로 태어나고 끝나면 사라지므로, 기억은 세션이 아니라 문서에 남긴다.

비유 — 응급실 분류(triage). 응급실 입구의 간호사는 치료하지 않는다. 환자를 보고 어느 과로 보낼지, 즉시 처치인지 정밀 검사인지 결정한다. 1단계의 PD가 그 역할이다. 분류가 틀리면 뒤의 모든 단계가 헛돈다. 그래서 PD는 분류 결과를 보고 첫머리에 [결정]/[피드백]/[질문]으로 명시하고, CJ는 분류부터 고칠 수 있다.

5. 운영 계약 요지

아래는 각 저장소 CLAUDE.md에 들어가는 계약의 요지다. 원문은 언제나 저장소 파일이 우선한다(7장).

  • 입력: CJ Comment가 유일한 런처. 매 보고 첫머리에 [결정]/[피드백]/[질문] 분류 표기.
  • 이슈: 코드 변경만 이슈화. 피드백 1건 = 에픽 1개 + Sub-issues(깊이 1단계). 종결은 CJ QA 통과 또는 묵시적 승인(다음 Comment 무이의).
  • 기획서 동기화: 규칙 변경 = Decision Log + 본문 섹션 동시 갱신. 보고에 "문서 반영 위치" 표 필수.
  • 문서 정리: 누적이 아니라 치환. 대규모 개정 후에는 eli-adult 정리본(DIGEST).
  • Notion 문서: 새 문서·갱신 시 Project=현재 프로젝트, Edit Date=실제 수정일, Editor=실제 Notion 사람 편집자. Agent·Mercury 표기는 Summary/본문의 운영 이력에만. Archive는 홀딩이고 삭제가 아니다 — 삭제는 현재 프로젝트 소속·대체/중복·연결 부재 3가지를 확인한 뒤에만, 다른 프로젝트·연결된 문서는 자동 삭제 금지.
  • Worker: 이벤트 구동 — 요청 시 기동, worker_done 보고, 검증 후 release. Worker는 git 쓰기 금지.
  • 역할 계약: 역할이 먼저, provider는 실행기. Venus=PLAN 전용(제품·런타임·빌드·도구·테스트 코드 수정 금지) · Mars=Client·HTML·Unity·툴링 구현 · Jupiter=Server 구현 · Saturn=읽기 전용 QA(제품·테스트 수정 금지) · Mercury=조정·Git·문서 메타데이터만. 같은 provider의 다른 역할이 비어 있어도 교차 역할 대체 금지.
  • 동일 역할 병렬화: 한 역할 하나면 기본 이름(Mars), 둘 이상이면 모두 안정된 접미사(Mars_1·Mars_2, Jupiter_1·Jupiter_2, Saturn_1·Saturn_2). 슬롯이 모자라면 같은 역할을 추가하거나 기다린다 — 다른 역할로 재분류하지 않는다.
  • dispatch preflight: 모든 dispatch는 required_role · mode · area · mutation · instance_index 5필드를 갖추고 역할 계약과 대조한다. 하나라도 어긋나면 role_scope_mismatch로 거부. worker_done도 같은 코드로 거부: Venus의 코드 아티팩트, Saturn의 파일 수정(제품·테스트 포함), 역할·인스턴스 불일치.
  • 확정/추론 구분: Agent 추론이 결정으로 둔갑하지 않게 모든 문서·보고에서 구분. 기획에 없으면 [기획 필요].

6. 세션 lease와 교대

AI 세션은 오래 쓸수록 나빠진다. 대화가 길어지면 압축(compaction)이 반복되고, 앞의 결정을 잊거나 오래된 상태를 현재로 착각한다. 이 구조는 그 문제를 “세션을 잘 관리”해서가 아니라 세션을 소모품으로 취급해서 푼다.

기본 규칙

독립 안건은 fresh Worker 기동 → worker_done → 결과 archive → release. 부서 Worker는 매 작업 fresh 세션이 기본이다. 같은 좁은 범위의 즉시 후속 작업만 부서별 최대 1개, 기한부 lease로 retain한다. 장수 세션(PD)은 스냅샷을 갱신한 뒤 교대한다.

retain(유지) 조건 — 모두 만족해야 한다

  • 직전 작업과 동일한 좁은 범위의 즉시 후속 작업일 것
  • 역할 인스턴스(Role 또는 Role_n)별 동시에 최대 1개만 retain
  • 기한부 lease — 기한 도래 또는 범위 이탈 시 release
  • retain 여부와 기한을 dispatch 기록에 남길 것

교대 신호 — 하나라도 보이면 교대한다

  • 마일스톤 종료
  • 컨텍스트 압축(compaction)이 반복됨
  • 문서·Task 상태와 세션 인식이 불일치
  • 스스로 판단력 저하를 감지 (자발적 재기동 요청)

교대 절차

  1. 인수인계 스냅샷을 치환 갱신 (누적 금지)
  2. 진행 중 이슈·dispatch 상태를 문서와 일치시킴
  3. 세션 종료(Clear) → 새 세션이 CLAUDE.md + 스냅샷 + 기준 문서를 읽고 인계
  4. 인계 후 첫 보고에서 스냅샷 기준일과 인계 사항을 명시

Mercury 창구(역할·접점)는 상설 유지한다. 교대되는 것은 내부 실행 세션이지 역할이 아니다.

비유 — 병동 근무 교대. 간호사는 8시간마다 바뀌지만 환자 차트는 이어진다. 교대 시 구두로 “이 환자 어제 열 났어요”라고 전하는 병동은 사고가 난다. 차트(스냅샷)를 갱신하고 다음 근무자가 차트를 읽고 시작하는 병동이 안전하다. “세션은 소모품, 문서가 기억”은 이 원칙의 다른 표현이다. 여기서 lease는 임대 계약처럼 “언제까지, 무엇을 위해” 세션을 붙들어 두는지 명시한 기한이다.

8. Notion 문서 수명주기 — 속성·Archive·삭제

문서가 기억이라면(2장), 그 기억이 어느 프로젝트의 것이고, 누가, 언제 만졌는지도 기억의 일부다. 그리고 기억을 치우는 일에는 “잠시 치워 둔다”와 “영구히 지운다”라는 전혀 다른 두 행동이 있다. rev 5는 이 둘을 Notion 문서 한 장의 일생으로 묶어 계약으로 만들었다. Notion 문서는 만들고 고치는 순간 세 속성(Project·Edit Date·Editor)이 사실과 일치해야 하고, 치우는 일은 Archive(홀딩)와 삭제 두 단계로 나눈다. 삭제는 세 가지 확인을 모두 통과한 문서에만 한다.

적용 범위: 이 구조를 쓰는 모든 프로젝트의 Notion 문서 — 기획서, 보고서, 스냅샷, Decision Log, 구조 정의 페이지. 작업 주체가 사람이든 Agent(Mercury 등)든 같다.

Project현재 작업 중인 프로젝트로 설정한다. 다른 프로젝트 값이 남아 있으면 갱신 시 바로잡는다.검색·필터·삭제 판정이 이 속성 하나에 기대므로 틀리면 다른 프로젝트 문서를 건드리게 된다.
Edit Date실제로 내용을 수정한 날짜로 설정한다. 과거 날짜를 그대로 두거나 미래 날짜를 넣지 않는다.스냅샷 기준일과 교대 판단이 이 날짜를 읽는다.
Editor실제 Notion 사람 편집자(person)를 넣는다. Agent 이름이나 Mercury 같은 부서명을 person 속성에 가짜 계정으로 넣지 않는다.person 속성은 알림·권한·책임 소재에 쓰인다. 존재하지 않는 사람을 만들면 책임이 사라진다.

Agent가 한 일은 어디에 적나. Agent나 Mercury가 작업했다는 사실이 필요하면 Summary 또는 본문의 운영 이력(날짜 · 부서 · 무엇을 바꿨나)으로 남긴다. 예: "2026-09-02 Mercury(Codex) — 진행도 표 치환". person 속성은 사람만 가리킨다.

치울 때 — Archive와 삭제는 다른 행동이다

상태뜻하는 일
Active현재 프로젝트가 참조하는 살아 있는 문서.속성 3종을 사실과 맞춘다. 치환 갱신.
Archive (홀딩)지금은 안 쓰지만 되돌릴 수 있게 보관하는 상태. 삭제가 아니다.Archive로 옮기거나 상태 속성을 Archive로 바꾼다. 내용과 연결은 그대로 둔다. 이유를 운영 이력에 한 줄 남긴다.
삭제되돌릴 수 없는 제거. Archive 문서 중 정말 불필요한 것만 대상이다.아래 삭제 전 확인 3가지를 모두 통과했을 때만 실행하고, 삭제 사실을 운영 이력(스냅샷 또는 상위 문서)에 남긴다.

삭제 전 확인 3가지 — 모두 통과해야 한다

확인통과실패하면
① 현재 프로젝트 소속Project 속성이 지금 작업 중인 프로젝트다.다른 프로젝트이거나 비어 있다 → 삭제 금지. 그 프로젝트 담당에게 넘긴다.
② 대체 또는 중복 사실같은 내용을 담은 최신 문서가 있거나(대체), 동일 문서가 둘 이상이다(중복). 대체 문서 링크를 적을 수 있다.대체 문서를 지목할 수 없다 → 삭제 금지. Archive에 남긴다.
③ 연결 부재Parent·Sub-Task·선행·후속·참조(백링크) 연결이 하나도 없다.연결이 하나라도 있다 → 삭제 금지. 연결을 먼저 정리할지 CJ에 [질문]으로 올린다.

자동 삭제 금지

  • 다른 프로젝트의 문서 (Project 속성이 현재 프로젝트가 아님)
  • 연결된 문서 (Parent·Sub-Task·선행·후속·참조 중 하나라도 있음)
  • 대체 문서를 지목할 수 없는 문서
  • Archive에 있다는 사실만으로는 삭제 사유가 되지 않는다

세 확인 중 하나라도 실패하면 삭제하지 않고 Archive(홀딩)에 둔 채 보고한다. 판단이 갈리는 문서는 Agent가 결정하지 않고 CJ에 [질문]으로 올린다.

Mercury (PD)가 수행한다. 규칙 자체의 변경은 CJ 승인 — 이 파일(structure.json)과 Notion 구조 페이지 Decision Log를 함께 갱신한다.

비유 — 도서관 폐기 심의. 도서관은 안 읽히는 책을 먼저 폐가 서고(Archive)로 내린다. 서가에서는 사라졌지만 요청하면 다시 나온다. 폐기는 별도 심의다: 우리 도서관 소장본인가(다른 관의 책을 우리가 버릴 수 없다), 새 판이 들어왔는가(대체), 다른 책의 참고문헌이나 시리즈 목록이 이 책을 가리키고 있는가(연결). 하나라도 걸리면 서고에 그대로 둔다. 그리고 폐기 대장에는 심의한 사서의 이름을 적는다 — 서고 운반 로봇의 이름이 아니라. 로봇이 옮겼다는 사실은 작업 일지에 남기면 된다.

9. 실제 예시

세 가지 예시를 든다. 첫 번째는 검증 프로젝트 Digit Dual에서 실제로 돈 사이클을 이 구조의 단계에 대응시킨 것이고, 두 번째는 패스트트랙의 전형적 형태이며, 세 번째는 이 구조를 새 프로젝트에 적용하는 절차다.

  1. ① 분류. PD(Mercury)가 세 안건을 [피드백]으로 분류한다. 셋 다 규칙 변경을 동반하므로 단순 지시가 아니다 → 풀 사이클.
  2. ②~④ 분석. 기획 영향(포획·도망·스와프 규칙)은 Venus, 클라이언트 구현 영향은 Mars가 각각 분석한다. Venus는 확정/추론/[기획 필요]를 구분해 선택지를 만든다.
  3. ⑤ 취합 보고. PD가 부서 분석을 한 장으로 취합하고, 각 안건에 판정과 권장안을 붙여 CJ에 보고한다.

# 1) 읽기만: 대상 프로젝트의 상태 진단 (쓰기 0)
node tools/bootstrap.mjs diagnose --target ../my-project

# 2) dry-run: 적용될 파일별 diff와 승인 토큰 출력 (대상에 쓰기 0)
node tools/bootstrap.mjs plan --target ../my-project --project-name "My Project" --out plan.json

# 3) 사람이 diff를 읽고 승인 — 출력된 토큰을 직접 전달한다
node tools/bootstrap.mjs apply --target ../my-project --plan plan.json --approve <토큰> --approved-by CJ

# 4) 검증: 적용된 파일이 lock의 SHA와 일치하는지 확인. 다시 plan을 돌리면 변경 0건이어야 한다
node tools/bootstrap.mjs status --target ../my-project

10. 흔한 오해와 알려진 운영 이슈

흔한 오해

  • “프롬프트를 안 붙이면 규칙이 무시된다” → 아니다. 저장소 CLAUDE.md가 모든 새 세션에 자동 적용된다.
  • “이슈를 사람이 직접 닫아야 한다” → 아니다. 묵시적 승인 규칙으로 PD가 근거와 함께 닫는다.
  • “부서가 많으면 항상 비싸다” → 아니다. 상시 터미널이 없는 이벤트 구동이라 일이 없으면 비용도 없다.
  • “이 HTML을 열면 프로젝트가 자동 세팅된다” → 아니다. 핸드북은 설명서일 뿐 어떤 코드도 실행하지 않는다. 적용은 bootstrap 도구가 진단→dry-run→사람 승인→apply 순서로만 한다.
  • “세션을 오래 유지할수록 똑똑해진다” → 아니다. 장수 세션은 압축이 반복되며 무뎌진다. 스냅샷을 갱신하고 교대하는 편이 능력 저하 없이 이어진다.
  • “Archive에 넣은 문서는 지워도 된다” → 아니다. Archive는 되돌릴 수 있는 홀딩이고 삭제는 되돌릴 수 없다. 삭제는 현재 프로젝트 소속·대체/중복·연결 부재 3가지를 확인한 문서에만, 다른 프로젝트나 연결된 문서는 자동 삭제하지 않는다.
  • “Mars가 바쁘고 Venus 세션이 비어 있으면 Venus가 구현해도 된다 (둘 다 Claude니까)” → 아니다. 역할이 먼저이고 provider는 실행기일 뿐이다. Mars_1이 바쁘면 Mars_2를 띄우거나 기다린다. Venus는 PLAN 전용이라 코드를 고친 worker_done은 role_scope_mismatch로 거부된다. 같은 이유로 Saturn은 어떤 파일도 고치지 않고, Mercury는 소규모 수정도 직접 하지 않는다.

알려진 운영 이슈와 대응

  • Worker 스폰 무한 대기 → fail: CLI 업데이트 확인 프롬프트가 Agent 기동을 가로챔 (Codex·Claude 공통 가능). 2026-09-02 codex 0.152.1 업데이트로 해결 사례. 대응 — ① CLI를 주기적으로 선제 업데이트 ② 기동 20초 후 터미널 생성 확인, 미생성 시 dispatch 상태 조회 후 1회 재기동 ③ 반복 시 사용자에게 업데이트 응답/앱 재시작 요청

11. 다른 프로젝트에 적용하기 — bootstrap

이전 버전(v3)의 핸드북은 “이 HTML을 Agent에게 주고 부트스트랩 블록을 붙여 넣으라”고 했다. 그 방식은 Agent가 무엇을 어떻게 바꿀지 사람이 미리 볼 수 없다는 약점이 있었다. v4부터는 사람이 diff를 읽고 승인해야만 파일이 바뀌는 도구로 대체한다.

도구가 하는 일

  • diagnose: 대상 폴더가 git 저장소인지, CLAUDE.md가 있는지, 이미 구조가 적용되어 있는지(버전·lock), 문서 폴더가 있는지를 읽고 권장 조치를 출력한다. 네트워크에 접근하지 않는다.
  • plan: 적용될 파일 집합을 렌더링해 현재 상태와 비교하고, 파일별 create/update/unchanged와 unified diff, 그리고 계획 내용의 해시로 만든 승인 토큰을 출력한다. 계획 파일(JSON)은 사람이 지정한 경로에만 쓴다.
  • apply: 계획 파일과 승인 토큰이 일치해야만 실행된다. 계획 시점에 기록한 “적용 전 해시”와 현재 파일이 다르면(drift) 아무것도 쓰지 않고 중단한다. 성공하면 .creat2ve/structure.lock.json에 버전·승인자·파일별 SHA-256을 기록한다.
  • status: lock에 기록된 SHA와 실제 파일을 대조해 변조·누락을 보고한다.

대상 프로젝트에 생기는 것

  • CLAUDE.md 안의 managed block: <!-- creat2ve:begin -->와 <!-- creat2ve:end --> 사이만 도구가 관리한다. 블록 밖의 프로젝트 고유 내용은 건드리지 않는다. 파일이 없으면 새로 만들고, 있으면 블록만 추가·치환한다.
  • docs/creat2ve/: 이 핸드북 사본(manifest의 SHA로 검증된 것), 권위 문서 등록표, 인수인계 스냅샷 초안, 부서별 수동 백업 Prompt, GitHub 라벨·마일스톤 권장안(JSON).
  • 파일 종류는 둘이다. managed 파일은 버전이 오르면 갱신되고, seed 파일(스냅샷·권위 문서 등록표)은 처음 한 번만 생성되고 이후에는 프로젝트 소유다.

도구가 하지 않는 일

  • GitHub 라벨·마일스톤·이슈 생성, Notion 페이지 생성. 이것은 사람이 승인한 뒤 PD가 수행한다. 도구는 권장안 JSON만 남긴다.
  • git add·commit·push. 적용 결과의 커밋은 사람 또는 Coordinator의 몫이다.
  • HTML을 열었을 때의 자동 실행. 핸드북에는 스크립트가 없다.

Agent에게 이 절차를 맡기려면 저장소의 skills/creat2ve-init/SKILL.md를 쓴다. 이 스킬은 진단 → plan → 사람에게 diff와 토큰을 보여주고 승인을 기다림 → apply → status 순서를 강제하며, 승인 없이 apply를 부르는 것을 금지한다.

비유 — 계약서 서명. 변호사(Agent)가 계약서 초안(plan)을 만들고 조항별 변경 사항(diff)을 표시한다. 서명(승인 토큰)은 의뢰인만 할 수 있고, 서명 후 초안이 몰래 바뀌었으면(drift) 계약은 무효다. 같은 계약서에 두 번 서명해도 의무가 두 배가 되지는 않는다(idempotent).

Project Director 역할 부서. Notion·GitHub·문서·보고·전달 허브. 접수창구는 상설, 내부 세션은 교대.
Worker
Orca Orchestration이 특정 작업을 위해 기동하는 부서 Agent 세션. 완료 시 worker_done을 보고하고 release된다.
Coordinator
Worker를 dispatch·감독·검증하고 커밋을 집행하는 세션. Phase 1에서는 감사역(Claude)이나 PD가 맡는다.
worker_done
Worker가 작업 종료를 알리는 단일 종결 메시지. 결과·수정 파일·남은 조건을 담는다.
release / retain
Worker 세션을 해제(release)하거나 기한부로 유지(retain)하는 결정. 기본은 release.
lease
retain된 세션에 붙는 기한과 범위 조건. 기한 도래·범위 이탈 시 자동으로 release 대상이 된다.
교대 (rotation)
장수 세션이 스냅샷을 갱신한 뒤 종료되고 새 세션이 문서로 인계받는 절차.
인수인계 스냅샷
프로젝트 현재 상태를 치환 갱신하는 단일 문서. 새 세션의 첫 읽기 대상.
fresh 세션
이전 대화 맥락 없이 CLAUDE.md와 문서만 읽고 시작하는 세션. 컨텍스트 오염이 없다.
교차 QA
구현한 모델(Claude)과 다른 모델(Codex)이 독립 검증하는 절차. 동종 편향 제거가 목적.
PASS / REVISE / BLOCKED
Saturn QA 판정. 통과 / 수정 후 재검 / 전제 불충족으로 진행 불가.
패스트트랙
단순 지시에 대해 분석·1차 보고를 생략하고 구현→QA→보고로 가는 경로.
에픽 / Sub-issue
피드백 1건을 부모 이슈로 만들고 파생 작업을 깊이 1단계의 자식 이슈로 연결하는 규칙.
묵시적 승인
완료 보고 후 CJ의 다음 Comment에 이의가 없으면 승인으로 간주해 이슈를 종결하는 규칙.
확정 / 추론 / [기획 필요]
보고·문서에서 결정된 사실, Agent의 추정, 기획에 없어 결정이 필요한 항목을 구분하는 표기.
Decision Log
기획서·구조 문서 안의 날짜별 결정 이력. 본문 치환과 함께 갱신한다.
DIGEST
마일스톤 종료·대규모 개정 후 eli-adult 스타일로 만드는 읽기 좋은 정리본.
권위 문서
어떤 주제에 대해 '진실'로 취급되는 문서. 충돌 시 우선순위 규칙을 따른다.
bootstrap
이 구조를 다른 프로젝트에 적용하는 절차. 진단 → dry-run diff → 사람 승인 → idempotent apply.
idempotent
같은 apply를 여러 번 실행해도 결과가 같고 두 번째부터는 변경이 없는 성질.
manifest
dist 산출물의 버전·파일·SHA-256 목록. 배포본이 원본과 같은지 검증하는 근거.
managed block
대상 프로젝트 CLAUDE.md 안에서 bootstrap이 관리하는 마커 구간. 구간 밖은 건드리지 않는다.
release / structure_revision
release는 이 저장소 산출물의 배포 버전(semver), structure_revision은 조직·규칙 개정 번호(정수). lock·manifest·핸드북에 둘 다 기록한다.
Notion 문서 수명주기
문서를 만들고(속성 3종 설정) → 쓰고(치환 갱신) → 홀딩하고(Archive) → 정말 불필요할 때만 지우는(삭제 전 확인 3가지) 규칙. rev 5에서 명문화.
Project / Edit Date / Editor
Notion 문서를 만들거나 고칠 때 반드시 사실과 맞춰야 하는 세 속성. 현재 프로젝트 · 실제 수정일 · 실제 사람 편집자.
Archive (홀딩)
지금 안 쓰는 문서를 되돌릴 수 있게 보관하는 상태. 삭제가 아니며, 삭제 사유도 아니다.
삭제 전 확인 3가지
현재 프로젝트 소속 · 대체/중복 사실 · Parent/Sub-Task/선행/후속/참조 연결 부재. 하나라도 실패하면 삭제하지 않는다.
역할 우선 배치
dispatch 때 작업의 영역·역할을 먼저 정하고 provider(Claude Code·Codex)는 그 역할의 실행기로만 붙이는 규칙. provider 가용성은 역할 선택을 되돌리지 못한다. rev 6에서 명문화.
역할 계약
역할별로 허용 mode·영역·산출물·mutation과 금지 행위·provider를 고정한 불변 표. Venus=PLAN 전용, Mars=Client·툴링 구현, Jupiter=Server 구현, Saturn=읽기 전용 QA, Mercury=조정·Git·문서 메타데이터.
Role_1 / Role_2 (동일 역할 복제)
같은 역할을 병렬로 둘 이상 돌릴 때 붙이는 안정된 접미사. 하나뿐이면 기본 이름(Mars)을 써도 된다. 슬롯 부족은 같은 역할 추가·대기로 풀고 다른 역할로 재분류하지 않는다.
dispatch preflight
Worker를 기동하기 전에 required_role · mode · area · mutation · instance_index 5필드를 역할 계약과 대조하는 검사. 어긋나면 dispatch를 만들지 않는다.
role_scope_mismatch
역할 계약 위반의 거부 코드. preflight 불일치, Venus의 코드 아티팩트, Saturn의 파일 수정, 역할·인스턴스 불일치 worker_done에 붙는다. 거부된 결과는 완료로 기록하지 않는다.

14. 변경 이력

번호는 둘이다. structure_revision(구조 개정 번호, 정수)은 조직·규칙이 바뀔 때 오르고, release(저장소 릴리스, semver)는 핸드북·도구·템플릿 산출물의 배포 단위다. 둘 다 source/structure.json이 원본이며 dist/manifest.json과 각 프로젝트의 lock에 함께 기록되어 npm run verify와 bootstrap status가 대조한다. rev 1~3은 저장소 이전 이력이라 릴리스 번호가 없다.
