# 1. 문제 — 지금 무엇이 안 되는가
Digit Duel에는 온라인 대전(PVP)이 이미 있습니다. 다만 지금은 **같은 공유기(LAN)에 물린 두 사람만** 함께 둘 수 있습니다. 서로 다른 회선(집 ↔ 카페, 서울 ↔ 부산)에서는 현재 구조로 접속할 수 없습니다.
## 1.1 지금 서버는 심판이 아니라 우체부입니다
지금 서버는 오가는 메시지의 **크기와 형식만 확인하고 내용은 읽지 않은 채 그대로 상대에게 전달**합니다. 게임 규칙을 판정하는 코드가 서버에는 아예 없습니다. 대신 두 브라우저가 같은 난수 씨앗(시드)을 나눠 갖고 **각자 자기 쪽에서 똑같이 계산**합니다. 두 사람이 같은 주사위를 던지기로 약속하고 각자 굴리는 셈입니다.
## 1.2 그래서 상대의 숨은 배치가 이미 내 브라우저 안에 있습니다
이 구조에서는 경기 시작 시점에 **두 브라우저 모두 상대의 전체 배치를 자기 메모리에 통째로 갖고 있습니다.** 화면에만 가려서 보여줄 뿐입니다. 브라우저 개발자 도구(F12)를 열 줄 아는 사람이면 상대가 어느 칸에 무엇을 숨겼는지 즉시 볼 수 있습니다.
지금까지 이게 문제가 되지 않은 이유는 단 하나 — **같은 방에 있는 믿을 만한 상대와만** 두는 것을 전제했기 때문입니다. 실제로 클라이언트는 사설 IP(집 공유기 안쪽) 주소만 받아들이고 공인 IP나 도메인 이름은 거부합니다.
## 1.3 "방"이라는 개념 자체가 서버에 없습니다
서버가 요구하는 접속 코드는 **방 단위가 아니라 서버 전체를 여는 열쇠 하나**입니다. 한 서버가 여러 쌍의 경기를 동시에 중계하는 것은 **이미 됩니다** — 없는 것은 "어느 방이 누구의 경기이고 지금 어떤 상태인가"를 서버가 기억하고 관리하는 **룸 객체**입니다. 이 구분이 중요합니다: 필요한 작업은 "동시 접속을 늘리는 것"이 아니라 "방을 만들고 관리하는 기능을 새로 만드는 것"입니다.
## 1.4 잠깐 끊기면 바로 몰수패입니다
소켓이 닫히는 순간 상대에게 "상대가 나갔다"가 전달되고 클라이언트는 그 자리에서 몰수패로 처리합니다. 유예 시간도, 재입장 수단도 없습니다.
<callout icon="⚠️" color="orange_bg">
	**한 줄 요약:** 외부망을 *그냥 여는 것*과, 이 게임의 핵심 재미인 *정체 숨기기를 지키면서* 외부망을 여는 것은 다른 문제입니다. 통신 암호화(TLS)만 얹으면 접속 자체는 됩니다. 하지만 그러면 §1.2의 노출이 **"같은 공유기의 지인"에서 "인터넷상 누구나"로** 넓어집니다.
</callout>
# 2. 제안 — 계정 없는 공개 로비 + 서버 권위 (2026-09-13 CJ 구현 승인)
아래는 **하나의 정합적인 묶음**입니다. 일부만 골라 채택하면 보안 효과가 성립하지 않으므로, 부분 채택은 설계가 아니라 절충이며 그 판단은 CJ가 따로 내려야 합니다.
## 2.1 큰 방향: 서버가 직접 판정하는 구조로 전환 (2026-09-13 CJ 승인 — 구현 착수 승인, 수치·파라미터는 Jupiter 구현 재량)
- **서버가 룸 상태를 소유하고, 각 좌석에는 그 사람이 봐도 되는 정보만 걸러 보냅니다.** 그러면 브라우저 메모리에 애초에 상대의 숨은 정보가 들어오지 않습니다.
- 구현 경로는 현재 `demo/index.html` 안에 있는 순수 규칙 로직(이동·전투·상성·폭탄·함정·밀어내기·판정·가시성)을 **서버와 클라이언트가 함께 쓰는 단일 JS 모듈**로 떼어내는 것입니다. 서버가 Node.js라 언어를 다시 짤 필요가 없고, 규칙이 두 벌로 갈라지는 위험도 피합니다.
- **작은 변경이 아닙니다.** 현재 규칙 로직은 화면 그리기 코드와 같은 함수 안에 섞여 있는 곳이 많아, 분리 자체가 별도 구현 이슈 규모입니다. 공수는 실측하지 않았으므로 이 문서는 기간을 제시하지 않습니다.
- **가벼운 대안**(현행 구조 + TLS만)도 기술적으로 가능합니다. 다만 §1.2의 노출이 그대로 남습니다. 둘 중 무엇을 고를지는 기술 문제가 아니라 **CJ의 제품 판단**입니다(§5 2번).

## 2.3 방의 상태와 "주인" (PROPOSED)
방은 **`대기 → 배치 → 진행 → 종료 → 정리`** 순으로 움직입니다. 여기에 **`취소`**(승패 없이 없어짐)와 **`무효`**(서버 재시작, §2.6)가 곁가지로 붙습니다.
- **"준비 완료"는 방의 상태가 아니라 좌석마다 켜고 끄는 스위치 두 개**입니다. 이것을 상태로 착각하면 "재접속하면 준비가 풀리나?" 같은 모순이 생깁니다. 규칙은 하나입니다: **자기가 배치를 바꿀 때만 자기 준비가 풀립니다. 재접속은 양쪽 준비를 건드리지 않고, 상대의 준비는 서버가 임의로 내리지 않습니다.**
- **상대가 준비했다는 사실 자체는 서로 보입니다.** 감춰야 하는 것은 *무엇을 어디에 놓았는가*와 *몇 개를 놓았는가*이지 제출 여부가 아닙니다 — 그게 없으면 "상대 준비 완료, 시작 대기 중" 화면이 성립하지 않습니다.
- **두 좌석은 순서 없이 동시에 배치합니다.** 한 사람이 상대 차례를 기다리지 않습니다(한 기기에서 번갈아 두는 핫시트 모드와 다릅니다).
- 방을 만든 사람이 호스트지만, **계정이 없으므로 "주인"은 그 세션 동안만 유효합니다.** 다음 날 다시 와도 서버는 그 사람을 기억하지 못합니다(의도한 설계입니다).
- 경기가 시작되면 "방장 권한"이라는 개념은 의미가 없어집니다 — 둘 다 대등한 플레이어입니다.

<td>유예를 주지 않습니다. 대기·배치 단계에서는 **그 자리에서 방이 취소**되고 정리됩니다. **진행 중에는 나가기가 없습니다** — 경기를 떠나는 유일한 방법은 기권이고 결과는 상대 승리입니다. 소켓을 끊는 쪽이 더 유리한 탈출구가 되지 않게 하기 위함입니다.</td>
</tr>
<tr>
<td>**연결 끊김**(와이파이·크래시)</td>
<td>의사 표시가 아닙니다</td>
<td>그 좌석의 **재접속 유예(60초, 제안)** 가 시작됩니다. 유예 안에 돌아오면 그대로 이어집니다.</td>
</tr>
</table>
유예가 **만료됐을 때의 결과는 단계마다 다릅니다.**
- **대기·배치 단계** → 방이 **취소**됩니다. 아직 시작 전이라 승패를 기록하지 않습니다. 게스트가 나가도 "호스트만 남아 다시 대기로 되돌아가는" 경로는 두지 않습니다 — 좌석 번호·배치·준비 상태를 어떻게 승계할지가 또 하나의 규칙 뭉치를 만들기 때문입니다. 호스트는 새 방을 만들면 되고, 비용은 코드를 한 번 더 전달하는 것뿐입니다.
- **진행 중** → 상대 좌석의 **몰수승**입니다.
- **둘 다 끊긴 경우 판정은 한 번뿐입니다.** 먼저 유예가 끝난 쪽에 대해서만 한 번 판정하고 경기를 끝냅니다. 나중에 두 번째 타이머가 끝나도 이미 끝난 경기이므로 아무 일도 하지 않습니다 — 양쪽 모두 승리로 기록되는 경로는 존재하지 않습니다. 선후를 가릴 수 없을 만큼 **동시에** 끝나면 **무승부(승자 기록 없음)** 입니다. 동전을 던져 한쪽을 고르지 않습니다.
- 상대 화면에는 이탈 사유를 밝히지 않고 **"상대가 다시 연결하는 중입니다… (남은 시간)"** 만 보여줍니다(정보전 유출 방지).
## 2.5 좌석을 증명하는 방법과 그 한계 (PROPOSED)
- 방에 들어오면 서버가 각 좌석에 **긴 임의의 비밀값(좌석 토큰)** 을 하나 줍니다. 이후 모든 행동은 이 값으로 "내가 이 좌석의 주인"임을 증명합니다. 계정 없이도 안전하게 확인할 수 있는 방법입니다.
- **토큰은 그 탭의 메모리에만 둡니다.** 주소·쿠키·브라우저 저장소 어디에도 쓰지 않습니다(현재 접속 코드를 다루는 방식과 같은 원칙).
- **그래서 새로고침하면 좌석을 잃습니다.** 재접속은 **같은 페이지가 살아 있는 동안의 네트워크 끊김**에만 적용됩니다. 새로고침 후 복귀는 이 묶음이 제안하지 않습니다 — 필요해지면 별도 안건입니다. <span color="red_bg">기획 필요</span>
- 같은 좌석으로 새 연결이 승인되면 **이전 소켓은 서버가 끊습니다.** 두 소켓이 동시에 같은 좌석의 명령을 넣는 구간이 남지 않게 하기 위함입니다. 이것은 토큰 탈취 자체를 막는 장치가 아니라 **동시 사용 창을 없애는** 장치입니다 — 이 문서는 보안을 보장하지 않습니다.
- 서버는 **누가 지금 입력할 차례인지**도 검사합니다. 지금은 이 검사가 화면(버튼 비활성화)에만 있어 개발자 도구로 우회할 수 있습니다. 특히 **도망 후 교환 선택은 현재 턴 플레이어가 아닌 쪽이 하는 경우가 있어**, 단순히 "지금 턴인 사람만 허용"으로 두면 정상 플레이가 막힙니다.
## 2.6 배포·재시작·롤백 — 규칙은 하나입니다 (PROPOSED)
- **룸 상태는 서버 메모리에만 있고 프로세스 수명을 넘지 못합니다. 프로세스가 바뀌면 살아 있던 모든 방은 무효입니다.** 계획된 재시작이든 갑작스러운 크래시든 결과가 같습니다. 차이는 **미리 알릴 수 있었는가**뿐입니다.
- 무효는 **몰수패가 아닙니다** — 플레이어 탓이 아니기 때문입니다. 화면에는 "서버 재시작으로 경기가 무효 처리되었습니다"라고 표시합니다.
- **계획된 재시작 절차(제안):** ① 진행 중인 모든 방에 **5분 예고**를 방송하고 그 시점부터 새 방 생성을 막습니다 → ② 예고 시간 동안 진행 중 경기가 자연히 끝나기를 기다립니다 → ③ 남은 방을 무효 처리하고 프로세스를 교체합니다. **짧은 공백이 생기며, 이 묶음은 그것을 없애려 하지 않습니다.**
- **무중단 배포(블루/그린)는 제안하지 않습니다.** 연결이 프로세스 사이를 옮겨갈 수 없고, 두 프로세스를 동시에 띄우면 "재접속을 원래 프로세스로 되돌리는" 고정 라우팅이 필요해집니다. 그 복잡도는 룸 상태를 외부 저장소로 뺀 뒤에야 의미가 있습니다(2단계).
- **롤백**은 이전 빌드를 같은 절차로 다시 배포하는 것입니다. **진행 중이던 경기는 복구되지 않습니다.** 다만 새 배포가 상태 점검에서 실패해 아직 교체 전이라면 기존 프로세스는 영향을 받지 않고 경기도 끊기지 않습니다.
- 초기 형태는 **소형 단일 인스턴스 + 메모리 룸 상태**입니다. 외부 저장소(Redis 등)로 빼는 것은 §7 지표가 필요를 보일 때의 2단계이며, 지금 분산 구조를 미리 만드는 것은 과설계입니다.
## 2.7 이번 묶음에 일부러 넣지 않은 것
- **계정 시스템** — 이번 제안은 계정 없이 코드만으로 동작합니다. 계정 도입은 완전히 별개 주제입니다. <span color="red_bg">기획 필요</span>
- **퀵매칭(낯선 사람과 자동 매칭)** — 비공개 룸을 **2주(제안)** 운영해 §7의 실측을 얻은 뒤 별도 안건으로 올립니다. **착수 기준 수치를 지금 정하지 않습니다** — 실측 없이 정한 목표치는 근거가 아니기 때문입니다.
- **공개 방 목록, 방장 권한 위임, 관전** — 초기 범위 밖입니다.
- **새로고침 후 좌석 복귀, 무중단 배포, 수평 확장** — §2.5·§2.6 참고.
## 2.2-B 방을 만들고 들어가는 흐름 — 공개 로비 (2026-09-13 CJ 구현 승인)
"어떻게 들어가는가"에 대한 답이 바뀌었다 — 초대 코드 대신 **방 목록을 보고 고른다.** 서버 상태 기계(§2.3)·좌석 토큰(§2.5)·배포·재시작(§2.6)은 이 변경과 무관하게 그대로 적용된다.
```javascript
방 목록 조회 → 원하는 방을 고르거나 새 방 생성 → 좌석 2개 확정
  → 각자 독립적으로 비공개 배치 → 양쪽 준비 완료 → 경기 시작
  → (끊기면 재접속 유예) → 승패 확정 → 방 자동 정리
```
- **계정을 만들지 않는다.** 서버가 발급하는 좌석 토큰(§2.5)이 그 세션의 인증이며, 공개 참가라는 사실이 그 인증 자체를 바꾸지 않는다. 좌석에 앉은 뒤의 행동 인가(소유권·행위자 검사)는 공개 참가 여부와 무관하게 동일하게 적용된다.
- 목록에는 **`대기`****(룸 상태기계의 ****`OPEN`****) 상태이며 좌석이 1개 빈 방만** 나온다. 배치·진행 중·종료된 방은 목록에서 빠진다(관전은 이번 승인 범위 밖과 일치).
- 방 식별자(`roomId`) 자체가 참가 키다 — 별도 초대 코드가 없다.
- (구현 선택) 호스트 표시명은 닉네임을 받지 않고 서버가 자동 생성한 레이블("방 #\<roomId\>")을 쓴다. 닉네임·채팅·랭킹/전적은 이번 최소안에 넣지 않는다 — 이번 승인 범위 밖과 별개로, 필요해지면 나중에 열 수 있는 확장이지 지금 막힌 선결 조건이 아니다.
- (구현 선택) 남용 방지: IP별 동시 대기 방 수 상한, 전체 동시 방 수 상한, 목록 조회 전용 속도 제한. 구체 수치는 파일럿 실측으로 교정할 초기값이며 개별 CJ 승인 없이 구현 단계에서 조정한다.
- 자세한 수용 기준·기본값은 `docs/milestone/v0.4.10/issues/217/Jupiter/public-rooms-analysis.md` §4·§5와 `docs/milestone/v0.4.10/issues/217/Venus/implementation-approval.md`에 있다.

# 6. QA·검증 상태
- **Saturn(Codex)의 설계 문서 검수와 잔여 문구 재검수를 완료했습니다(2026-09-13).** Mercury가 기본 검수 `msg_7a1d92bd5a25`와 최종 차이 검수 PASS `msg_adc2ad321758`를 취합했습니다. 이 결과는 문서 정합성에 한정되며 구현·보안·런타임 QA와 CJ 승인을 대체하지 않습니다. **이 QA는 §2.2-A(비공개 초대 코드, SUPERSEDED) 번들에 한정되며, 새로 승인된 §2.2-B 공개 로비에는 적용되지 않는다 — 구현물이 나오면 별도 Saturn 검수가 필요하다. 서버 권위 전환과 공개 로비 구현 승인은 이미 난 CJ 결정이라 이 문서가 재승인을 요청하지 않는다.**
- **공개 로비 가능성 검토(2026-09-13, Jupiter 분석) → CJ 구현 승인으로 귀결:** 같은 서버 권위 룸 코어 위에 방 목록/수동 참가를 올리는 공개 룸은 기술적으로 가능하며 자동 매칭(퀵매칭)과는 별개 주제라는 것이 Jupiter의 초기 결론이다(`docs/milestone/v0.4.10/issues/217/Jupiter/public-rooms-analysis.md`). 목록/조회/참가가능 메타데이터/채널/원자적 입장·남용 방지가 추가 구성요소로 거론되었다. 2026-09-13 CJ가 이 분석을 근거로 공개 로비의 구현 착수를 승인했다(§2.2-B). 구체 수치(레이블 형식·속도 제한값 등)은 여전히 Jupiter/Mars 구현 재량이고 CJ가 문장 그대로 지시한 것은 아니다.
- Saturn이 짚어 반영된 주요 항목: 공개된 말의 미공개 기술 노출 / 두 좌석의 독립 배치 인가 / 재접속 자격에 서버 세대(epoch)를 싣는 방법 / 응답이 연속 유실될 때의 토큰 처리 / 명시적 이탈과 소켓 단절의 구분 / 양측 단절 시 이중 승리 차단.
- **서버 권위 전환과 §2.2-B 공개 로비의 코드 구현은 2026-09-13 CJ 승인으로 착수 가능하다. 외부망 배포(호스팅·도메인 구매)는 여전히 별도 결정 대기입니다(§5).**
- 이 문서는 **보안을 보장하지 않습니다.** §2.5는 "동시 사용 창을 없앤다"이지 "토큰 탈취를 막는다"가 아니고, §4의 노출 차단은 "서버가 보내지 않는다"이지 "클라이언트가 안전하다"가 아닙니다.
- **성능·용량·공수를 주장하지 않습니다.** §2·§7의 모든 수치는 실측 근거가 없는 초기 제안값이며 파일럿에서 교정할 대상입니다.
