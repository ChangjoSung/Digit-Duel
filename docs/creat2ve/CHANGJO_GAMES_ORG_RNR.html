전달·조정 원칙

  • CJ Comment를 결정·피드백·질문으로 분류하고, 승인된 범위만 구체화한다. 단순 지시는 필요한 수정·검증으로 바로 진행한다. 복합 안건은 소관 분석 → PM 취합 → CJ 방향 결정 → 구현 → Saturn 검수 → CJ QA → 정리 순서다.
  • 역할을 먼저 정하고 모델을 배정한다. 공급자나 빈 슬롯을 이유로 다른 역할이 대신하지 않는다. 같은 역할이 병렬이면 모두 Role_1, Role_2처럼 안정된 접미사를 쓰고 기본 이름과 index 1을 중복 배정하지 않는다.
  • dispatch에는 required_role / mode / area / mutation / instance_index, 정확한 workspace·기준 ref/SHA·파일 범위·보존 조건·완료 기준·필수 검사와 기본 1회 제한을 기록한다. 역할·경로가 어긋나면 role_scope_mismatch로 거부한다.
  • 산출물은 workspace 상대 경로다. 상위 이동·절대/드라이브/UNC/URL 경로·중첩 퍼센트 인코딩·끝점/공백 세그먼트·제어/유니코드 구분자·금지 문자·실행/코드 마커가 숨은 자산 파일명을 허용하지 않는다. 거부된 결과를 완료로 기록하지 않는다.
  • Worker는 결과를 판정·변경 파일·검사·미해결·증거 링크로 짧게 전달한다. 같은 현재 상태를 적는 역할별 Markdown 보고서를 새로 만들지 않는다. PM이 이 HTML의 해당 항목을 갱신한다. 기계 로그·원본 영수증은 별도 증거로 보존한다.

  1. 일반 흐름: 이슈 브랜치 → squash → milestone/vX.Y.Z → merge commit → dev → merge commit → main + tag/Release. 보호 main·dev·트랙에 직접 커밋하지 않는다. 트랙은 dev에서, 이슈 브랜치는 해당 원격 트랙에서 분기한다.

  3. 브랜치명은 feature/·fix/·infra/·doc/와 작업 식별자를 쓴다. 제목·본문은 한국어와 scope를 사용하고 코드/자산 변경은 납품 목표별 Issue 1개·통합 PR 1개로 관리한다. 문서/운영 결정만으로 역할별 Issue를 증식시키지 않는다.
