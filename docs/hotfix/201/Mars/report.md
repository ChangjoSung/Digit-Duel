작성 2026-09-11 · 작업 공간 `hotfix-201-online-art` · 기준 `origin/main ff6e87a` (v0.4.6 출시본)
소관: **클라이언트 표시 계층만**. `server/**` 는 Jupiter 소관이며 이 보고서는 읽기만 했다.

## 1. 증상과 원인 (확정)

CJ 스크린샷(온라인 P2 · 턴 17)에서 왕은 👑, 동료는 🤝 이모지로, 번개 지속형 하수인 한 종만 텍스트 이름으로
남고 나머지 하수인은 정상 아트였다.

**정상 동작이라 고치지 않은 것** — 같은 화면 안의 다음 세 가지는 결손이 아니다.

| 화면 | 판정 |
|---|---|
| 상단 `?` 타일 | 규격 7.10.3 미공개 은폐. 미공개 말에는 `<img>`·src 자체가 만들어지지 않는다 |
| 💣 폭탄 | 폭탄·함정에는 아트 규격이 없다 — `MEMO_OPTS` 기호 어휘 (`demo/index.html:734`) |
| "함정" 텍스트 | 🪤(U+1FAA4) 글리프가 Windows 10 설치 폰트에 없어 같은 뜻의 짧은 라벨로 대체 (`glyphOk`, `demo/index.html:1015-1038`). 문서화된 계약이다 |

**실제 결손의 원인 (클라이언트)** — 자산은 디스크에 전부 있다(하수인 20종 × 5파일, 리더 4파일, 매니페스트 대조 완료).
문제는 **한 번의 일시적 로드 실패가 영구 실패로 굳는 것**이었다.

- `artFail` 이 `ART.failed` 에 종을 추가하면 되돌릴 경로가 없었다 — 페이지를 새로 열기 전까지.
- 왕·동료는 더 심했다: `leaderArtDir` 이 `ART.loaded` 확인을 요구하는데 그 집합을 채우는 곳이
  **1회성 `artPreload` 뿐**이라, 프리로드에서 한 건 놓치면 그 탭에서는 영영 이모지였다.
- 온라인에서만 보인 이유: `file://` 에는 요청 한도가 없다. HTTP 경로에는 IP당 토큰 버킷이 있었고,
  종전 예산(버스트 60·초당 30)은 냉시작 45건을 겨우 담아 같은 IP의 두 번째 로드가 겹치면 절반 가까이 429 였다.
  **서버 쪽 예산 상향은 Jupiter 가 별도로 처리했다** (이 보고서 범위 밖).

### 초기 가설 중 틀린 것 (실측으로 기각)

진단 단계에서 "`Cache-Control: no-store` 때문에 `render()` 마다 같은 아이콘이 다시 요청되어 요청이 폭증한다"고
추정했다. **실제 브라우저 측정에서 사실이 아니었다** — 헤드리스 Chrome 에서 `render()` 12회 뒤 같은 자산 URL 의
추가 HTTP 응답은 **0건**이다(`report.json` → `noStore.delta = 0`). 브라우저가 메모리 이미지 캐시로 재사용한다.
따라서 이 HotFix 의 근거는 "요청 폭증"이 아니라 **"한 번의 실패가 영구히 굳는 것"** 하나다.

## 2. 바꾼 것 (표시 계층 전용)

규칙·수치·RNG·온라인 프로토콜·전투 연출 타이밍·튜토리얼은 하나도 건드리지 않았다.

### `demo/index.html` — 유한 복구 엔진

| 위치 | 내용 |
|---|---|
| `ART` 상태 | `retry`(파일 단위 예산)·`gone`(영구 결손 파일)·`settled`(그 종에 남은 일 없음) 추가 |
| `ART_RETRY` | `max:3`(연속 실패 상한) · `hardMax:8`(파일당 절대 조회 상한) · `delays:[400,1200,3600]` · `deadlineMs:5000` |
| `artScheduleRecovery(dir, force)` | 실제로 떨어진 파일만 지목해 예약한다. 이미 확인된 파일은 덤으로 부르지 않는다 (예외: 그 종이 폴백이면 아이콘은 다시 확인 — 보드 얼굴을 되돌릴 유일한 근거) |
| `artScheduleFile` | 파일당 예약 1개·조회 1개. `gone` 이면 즉시 반환 |
| `artProbeFile` | **능동 마감**: 조회마다 `deadlineMs` 시한을 걸고, 끝날 때 마감 타이머를 끄고 `onload`/`onerror` 를 떼어낸다. 뒤늦게 오는 이벤트가 상태를 다시 건드리지 못한다. 판정은 전부 **이번 조회 결과**로만 한다 |
| `artFail` | 이미 실패로 기록된 종이어도 예약을 매번 시도한다(겹침은 예약·진행 중 검사가 거른다). 재그리기는 종전대로 상태가 바뀔 때 한 번만 |
| `artSpriteFail` | 기존 계약(그 종을 실패로 기록·`onerror` 절단·토큰 즉시 교체)은 그대로 두고, 실패한 **전투 파일**을 지목해 복구를 예약 |
| `artBattleOk(dir)` | 전투 토큰이 **영구 결손으로 판정된 전투 파일을 다시 내보내지 않는다** |
| `leaderArtDir` / `leaderBattleDir` | 과거 기록(`ART.loaded`)만 보던 것을 고쳐 `artGone` 도 함께 본다 — 왕·동료의 죽은 `battle256` 이 전투창마다 다시 요청되지 않는다 (Saturn P2) |
| `artRerender` | `artFail`·`artLeaderReady`·복구 성공이 공유하는 1회 예약 자리로 통합 |

**유한성**: 파일당 연속 실패 3회 또는 누적 8회에서 `gone` 으로 굳는다. 응답이 오지도 끊기지도 않는 요청도
능동 마감이 끝낸다. 성공은 연속 실패 기록만 되돌리고 누적 상한은 그대로라, 성공/실패를 오가는 병적인 경우에도
요청이 늘어나지 않는다.

**정보 경계 (불변)**: 조회 대상은 프리로드가 쓰는 바로 그 파일이다 — 새 URL 0건. 촉발 지점도 종전과 같다:
정체와 무관한 고정 44 프리로드 집합, 그리고 **이미 공개된 말이 이미 내보내던 `<img>`** 뿐이다.
미공개 말에는 여전히 `<img>`·src·alt·클래스 어디에도 정체 값이 생기지 않는다.

## 5. 실제 브라우저 증빙 (34 / 34 통과)

내가 띄운 `server/server.js`(루프백 임의 포트, 이 실행 전용 접속 코드 주입)와 내가 만든 헤드리스 Chrome
임시 프로필에서, **독립된 두 탭**이 실제 로비 입력칸·버튼 클릭으로 인증·매칭을 거쳐 로스터 선택·배치를 지나
보드까지 갔다. 종료 시 내가 띄운 PID·내가 만든 경로만 정리했다(사용자의 서버·프로세스는 건드리지 않았다).

- **냉시작 2인**: 양쪽 모두 고정 44 집합을 누락 0으로 요청, 자연 발생 실패 0건. 그 밖 6건은 내가 누른
  로스터 카드의 설명창 일러스트다(말의 정체와 무관).
- **아트**: 두 좌석 모두 왕·동료·하수인 6/6 이 실제 아트. 미공개 상대 말 칸에는 `<img>`·자산 경로 0건 (`?` 유지).
- **실제 합법 수 + 동기화**: 말 1개를 실제로 이동시킨 뒤 **28개 말 전부의 논리 좌표·HP·생존 다이제스트가
  양쪽에서 동일**했고, 움직인 그 말이 양쪽에서 같은 칸(11,7)에 있었다.
- **유도 429 대조**: 같은 조건에서 현행 소스는 스스로 복구했고, **기준판 소스를 CDP 로 문서 본문만 바꿔 끼운**
  탭은 왕이 이모지로 남았다 — CJ 스크린샷의 증상 그대로다. 저장소 파일은 바꾸지 않았다.
- **유도/자연 구분**: 유도 429 는 `induced:true` 로 기록하고 같은 응답을 자연 실패로 두 번 세지 않는다.
  최종 실행의 자연 발생 자산 실패는 **0건**, 유도는 **2건**이다.
- **연속 새로고침 4회**: 자산 실패 응답 0건, 실패한 종 0건.
- **no-store 측정**: `render()` 12회 뒤 같은 자산의 추가 응답 **0건** (위 §1 참조).

## 7. 한계·미확정

- **실제 온라인 전투 촬영은 하지 않았다.** 위 §5 의 픽스처 표기를 소급해 "실제로 둔 전투"로 바꾸지 말 것.
- **`no-store` 재요청은 관측 결과 0건**이다. 이 값은 헤드리스 Chrome 1개 버전·1회 측정이며, 다른 브라우저·
  버전에서 같다고 일반화하지 않는다. 판정이 아니라 기록이다.
- **유도 429 는 CDP 로 주입한 모의 실패**다. 이 실행에서 자연 발생한 429 는 0건이며, 서버 예산 상향의
  실측 대조는 Jupiter 보고서 소관이다.
- **Saturn 교차 QA (Codex · 독립 READ_ONLY): PASS** — 산출물 수정 0건(`files_modified=[]`)으로 보고됐고
  Mercury 가 `qa.md` 에 보존한다. 판정 원본은 Saturn 보고서이며 이 문서는 구현자 자기 보고다.
- README 갤러리 교체는 **같은 Issue #201 범위**이며 별건이 아니다. 경로·캡션 편집은 Mercury 소관이다.
- CJ 최초 신고 화면(턴 17 · 특정 종)의 **그 순간 429 로그는 남아 있지 않다**. 원인 설명은 소스 경로와
  재현으로 뒷받침했을 뿐, 그때의 네트워크 기록을 복원한 것은 아니다.
- 이 보고서는 README 에 쓸 촬영물과 해시를 제공할 뿐 README 자체를 건드리지 않았다.
